# 远程解锁锁屏 —— 设计与安全边界（2026-11-07）

状态：**设计稿，未实现**（用户选择"先出设计，不急"）。实现前必须先过一遍本文的风险清单。

---

## 1. 目标与非目标

**目标**
- 电脑处于**锁屏**状态时，手机能输入密码把桌面解锁，然后继续操作（等同人在电脑前输密码）。
- 自用版默认可开；**发布版默认关闭**，用户显式开启并二次确认风险。

**非目标**
- 不保存、不缓存、不代填任何密码。
- 不绕过 Windows 凭据体系（不写注册表改密码、不禁用安全策略）。
- 不解决"注销后无人登录"的场景（那需要自动登录，属另一条策略，见 §7）。

---

## 2. 现状与限制（为什么现在解不了锁）

| 事实 | 影响 |
|---|---|
| 锁屏后前台是 **Winlogon / LogonUI 安全桌面** | 普通进程（哪怕管理员）的 `SendInput` 被 UIPI + 桌面隔离拦掉 |
| 我们的 `input.exe` 是 **`ccj` / Highest** 身份、跑在用户会话 | 只能操作普通桌面；锁屏时按键**全部无效**（产品现在就是"能看到锁屏画面，但敲不进密码"） |
| `input.exe` 用 `SendInput` 注入 | 改成 SYSTEM 也不够——**必须附着到 Winlogon 桌面**才能真正送达 |

结论：想在软件层解锁，必须引入一个**能在安全桌面上注入**的组件，或改用**凭据提供程序**。

---

## 3. 三条可选路线

| | A. 系统设置（不注入） | B. SYSTEM 安全桌面注入 | C. 凭据提供程序（Credential Provider） |
|---|---|---|---|
| 做法 | 关掉"唤醒需要登录"、关屏保锁屏 | SYSTEM 组件附着 Winlogon 桌面 `SendInput` | LogonUI 加载我们签名的 CP DLL，接收密码完成解锁 |
| 效果 | 唤醒后**直接回桌面**，无需密码 | 锁屏时**手机输密码解锁**（和 UU 远程一样） | 同上，还可以做"扫码/免密" |
| 代价 | 物理接触者无需密码 | 密码经我们通道；SYSTEM 组件是高价值攻击面 | 需要 C++/C# DLL + **代码签名证书** + 安装逻辑 |
| 风险 | 中（丢设备即丢机器） | 高（必须严格设计，见 §5） | 中（走官方机制，签名可校验） |
| 工作量 | 10 分钟 | 2-4 天（含 PoC） | 3-5 天 + 证书 |
| 两轨策略 | 自用版默认开 | 发布版默认关、自用版可开 | 发布版可选 |

**推荐**：短期用 A 解决"唤醒即用"；需要"真·锁屏解锁"时做 B，且**只放在自用版**先行验证；C 作为长期正规化方案。

## 4. B 的架构

```
手机页面（已鉴权）
   │  POST /unlock  { password }        ← 仅 HTTPS + 产品 key + 已建立会话
   ▼
screen-server.mjs（用户会话，ccj）
   │  命名管道 \\.\pipe\dsh-unlock      ← ACL: SYSTEM + 当前用户
   ▼
unlock-helper.exe（SYSTEM，会话 1）
   │  OpenDesktop("Winlogon") → SetThreadDesktop → 校验前台类名 LogonUI
   ▼
SendInput: 逐字符 VK/Unicode → Enter → ZeroMemory
```

**两级进程**（关键约束）：
- SYSTEM 计划任务跑在 **session 0**，无法直接看到 session 1 的安全桌面；
- 所以 helper 需要一个**会话内**子进程：守护进程用 `WTSGetActiveConsoleSessionId()` +
  `DuplicateTokenEx`(自身 SYSTEM token) + `SetTokenInformation(TokenSessionId=1)` +
  `CreateProcessAsUser` 在会话 1 拉起 worker；
- worker 附着 Winlogon 桌面执行注入，注入完退出；守护留在 session 0 等人连管道。

**为什么不用现成的 `input.exe`**：它是用户会话 + `SendInput`，天然够不到安全桌面；把注入逻辑拆成独立 SYSTEM 组件，风险面更小、也便于默认关闭。

## 5. 密码与安全设计（必须逐条落实）

**密码处理**
1. 只在内存中：页面输入框提交后立即清空；screen-server 用 `Buffer` 转发后 **zero**；
   worker 注入后 `ZeroMemory`。**任何环节不得写日志/文件/崩溃转储**。
2. 不提供"记住密码"；不写入 `credential manager`。
3. 传输：仅经 HTTPS（tailnet / 回环），且要求已有鉴权会话；**不接受跨源请求**。

**权限与调用方校验**
4. 管道 ACL 只给 `SYSTEM` + 当前登录用户；`GetNamedPipeClientProcessId` 校验调用进程
   镜像路径 == 产品目录下的 screen-server，且会话号匹配，否则拒绝。
5. worker 执行前校验：目标是 `Winlogon` 桌面、前台窗口类名是 `LogonUI`；否则立刻放弃（错误码明确）。

**限流与审计**
6. 频率：60 秒内最多 3 次尝试；连续失败 5 次锁定 10 分钟（防远程暴力试密码）。
7. 审计日志只记：时间、来源会话、结果（成功/失败/拒绝原因）、耗时；**绝不记密码**。
8. 界面显式确认："这台电脑已锁屏，输入密码解锁" —— 避免误触把密码打到别处。

**开关与两轨**
9. `product.config.json` 增加 `security.remoteUnlock`（默认 false）。
10. **发布版强制默认 false**，开启时要二次确认并展示风险说明；自用版可默认 true。
11. 关闭时 worker 不安装/不启动，管道不存在 —— 不留后门。

**已知风险（必须向用户明说）**
- B 等于把"解锁能力"放进 SYSTEM 组件：能连上管道的本机进程理论上可滥用 → 只能靠 ACL +
  调用方校验 + 限流降低，**无法根除**；这是所有"远程解锁"类产品的共同代价。
- 手机丢失/被控 → 攻击者可解锁电脑；必须配合设备的锁屏密码和 tailnet ACL。

## 6. 失败与回退

| 情况 | 行为 |
|---|---|
| 没锁屏 | 直接返回 `not_locked`，页面提示"当前没有锁屏，可直接操作" |
| 附着桌面失败 | 返回 `secure_desktop_unavailable` + 错误码，不重试 |
| 密码错误 | 返回 `rejected`（Windows 自己会显示"密码错误"），计入限流 |
| 超时（8 秒内没看到登录界面变化） | 返回 `timeout`，只重试 1 次 |
| 用户拒绝/关闭功能 | 端点直接 403，管道不监听 |

---

## 7. 与"自动登录"的区别（别混淆）

- **自动登录（netplwiz）**：解决"重启后没人登录"，登录后仍会锁屏；
- **A 路线（关唤醒需登录）**：解决"唤醒/锁屏后要输密码"；
- **B 路线**：解决"锁屏时远程输密码"，不依赖上面两条。
三者可以叠加，但每叠加一条都会降低物理安全性，**自用版**才建议全开。

---

## 8. 验收清单（实现后逐条测）

1. 锁屏 + 正确密码 → 解锁成功，手机端画面进入桌面；
2. 锁屏 + 错误密码 → 明确失败，**日志里搜不到密码**；
3. 非锁屏状态调用 → `not_locked`；
4. 无权限/未鉴权调用 → 403；
5. 连续 5 次失败 → 锁定 10 分钟；
6. 重启后：功能开→worker 自启；功能关→无进程、无管道；
7. 发布版默认关闭，开启需二次确认；
8. 崩溃/断电后不残留明文。

## 10. P0 实测结果（2026-11-08，联想 83LT / Win10 22H2）

按 §9 先做 P0，结论**部分可行**，并发现一个关键限制：

| 验证项 | 结果 | 证据 |
|---|---|---|
| SYSTEM(会话0) → 复制令牌 → `TokenSessionId=1` → `CreateProcessAsUser` | ✅ 成功 | 子进程 `cmd.exe` 在会话 1 执行并写出文件（exit 0） |
| 在 `winsta0\Winlogon` 桌面创建进程 | ✅ 成功 | 同一命令在 Winlogon 桌面上也写出了文件 |
| **托管代码（.NET）在该上下文运行** | ❌ **失败** | 连 `hello.exe`（只写一个文件）都返回 `0x8007045A ERROR_DLL_INIT_FAILED`；我们的注入器、`input.exe` 同类 |
| 原生 exe（cmd.exe / python.exe） | ✅ 可以启动 | python 能打印 banner；但 `_ctypes` 扩展加载同样报 DLL 初始化失败 |
| 补 `CreateEnvironmentBlock` 环境块 | 不影响结论 | 环境块已正确创建，仍失败 |

**根因判断**：用"复制令牌 + 改 TokenSessionId"创建的进程，**CLR / 部分原生扩展无法初始化**
（Windows 对这类会话迁移进程的加载器行为限制）。这不是代码写错，是平台限制。

**对方案的修订**：
- B 方案的注入组件**必须是原生（C/C++）exe**，不能是 .NET；
- 本机没有 cl/gcc/clang/tcc，编译原生组件需要先装工具链（MSVC Build Tools ≈1–2GB，或 mingw-w64）；
- 另一个思路：不迁移会话，改为**安装一个 SYSTEM 服务**（session 0），由服务在会话 1 用
  `WTSQueryUserToken` 拿用户令牌起进程——但用户令牌**打不开 Winlogon 桌面**（权限不够），
  所以"服务 + 原生 helper"仍需要原生代码。

**因此下一步取决于工具链**：装不装 MSVC/mingw，或者由我在别的机器上编译好原生 helper 再拿过来。
在新工具链就位前，B 方案无法继续 P1。
