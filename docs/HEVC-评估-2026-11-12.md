# HEVC（H.265）硬编/硬解评估 —— 2026-11-12

> 背景：H.264 已经优化到"关键帧 114KB、PLI 29→2、画出 98~100%"。下一步最大的杠杆是**换编码器**
> （同等画质省带宽、关键帧更小）。这份文档只回答三件事：**当前是什么状态、值不值得做、代价多大**。

## 结论先行

- **技术上可行**：GPU、Chrome（WebCodecs HEVC + WebRTC H.265）、Pion（默认注册了 H.265、有解包器）全都就绪；
  唯一硬缺口是**自带的精简版 ffmpeg 完全没有 HEVC**——已经在本机重编出来（见下），可编可解。
- **收益（本轮实测，同一段抓屏、同码率、同 GOP）**：等码率下 **Y-PSNR 高 1.23~1.25 dB**（8Mbps 38.83→40.08，
  20Mbps 44.77→46.00）；按"1.25dB ≈ 25~30% 码率"的经验换算，**等画质大约省 20~30% 带宽**。
  ——"省 30%"这个标准说法在我们的桌面内容上是成立的，但没有宣传的那么夸张。
- **代价**：4 个组件都要动（ffmpeg 重编 / 服务端 fMP4+参数集 / 侧车 H.265 打包 / 页面 HEVC 解码），
  外加**能力探测 + H.264 回退**；商用分发还要评估 HEVC 专利池。
- **建议**：技术上过关、收益真实（~1.2dB），**手机端也已实测支持**（`hevc=1/1/1/1`），可以进 P1；
  仍建议默认走 H.264、HEVC 用灰度开关，因为老设备/其他机型未必都有硬解。

## 一、当前情况（逐环节，都是本轮实测/可核对的事实）

| 环节 | 现状 | 证据 |
|---|---|---|
| GPU | RTX 5070 Laptop：NVENC/NVDEC 支持 HEVC 8/10bit | 规格 |
| **自带 ffmpeg** | **完全没有 HEVC**：只能 `h264_nvenc,h264_mf`；无 hevc 解析、无 hevc 解码 | `ffmpeg -encoders / -decoders` + `-version` 的 configure 行 |
| 重编条件 | MSYS2 工具链、FFmpeg 8.1.3 源码、nv-codec-headers 都在本机；上一版 configure 命令可原样复现 | `D:\build\*`、`ffbuild/config.log` |
| 浏览器 WebCodecs | `hvc1.1.6.L120.90` / `hev1.1.6.L120.90` / Main10（`hvc1.2.4.L120.B0`）**全部 supported** | 本机 Chrome 实测 `VideoDecoder.isConfigSupported` |
| 浏览器 WebRTC | `RTCRtpSender/Receiver.getCapabilities('video')` 里**有 `video/H265`**（PT 待协商） | 本机 Chrome 实测 |
| **手机（真机实测）** | APK（WebView）与浏览器端都报 **`hevc=1/1/1/1`**：WebCodecs 能配 hvc1、**有硬件解码器**、Main10 也支持、WebRTC 能力含 video/H265 | 页面探针（`hevc=` 字段）实测 |
| 侧车（Pion v4.2.26） | `MediaEngine` 默认注册了 `MimeTypeH265`（PT 116）；`pion/rtp` 有 **H265Depacketizer**；**没有 H265Payloader** | go mod 缓存源码 |
| 产品接收端 | `wc264-worker.js` 只认 H.264：NAL 5=IDR、SPS/PPS=7/8、avcC；fMP4 解析同理 | 代码 |
| 服务端 | `h264ExtractSamples/h264ParseMoov` 是 H.264 专用（avcC、sync 位、NAL 类型） | 代码 |

一句话：**代码里"从编码到解包"整条链路都是 H.264 专用，但我们的运输层（WebRTC + 自研接收端）已经具备接 H.265 的条件。**

## 二、优势（机制 + 对我们的具体意义）

1. **带宽省 25~40%（同画质）**。我们当前 1920x1200@120 是 **20Mbps**，每帧预算只有 ~20KB。
   同画质下 HEVC 能把预算降到 13~15Mbps，或者**把省下的码率换成"更清晰的帧内质量"**——
   对"远控看文字/表格"这种场景，清晰度提升比码率数字更有价值。
2. **关键帧更小**。HEVC 的 I 帧效率比 H.264 高，这对我们已经治过的"关键帧突发"是再降一档：
   H.264 现状关键帧 114KB（intra-refresh 后），HEVC 预计 ~70~80KB，突发更平。
3. **弱网价值最大**：4G/公共 WiFi 上 20Mbps 常常跑不满，HEVC 能让"同样清晰度所需带宽"降一档，
   直接减少自动降码率/降档的触发频率。
4. **10bit/HDR 的唯一路**：H.264 不支持 HDR；以后要做 HDR 只能走 HEVC Main10（本机 Chrome 已支持该 profile）。
5. **硬件都是现成的**：NVENC 编码、手机/PC 硬解，CPU 占用几乎不变；我们已经有 intra-refresh /
   keyframe 控制这套调优经验，可以直接复用到 hevc_nvenc。

## 三、劣势与风险（按严重度排序）

1. **兼容性分裂（最大风险）**：Chrome 在本机（Windows + N 卡）支持 HEVC WebCodecs/WebRTC，
   **本机手机两个端已实测支持**（`hevc=1/1/1/1`）；但 Safari/iOS 走 HEVC 需要 iOS 17+ 且设备有硬解，老安卓/无硬解设备仍不支持。
   → 必须**保留 H.264 路径**并在连接前探测能力，探测失败就回退；否则用户看到的是黑屏。
2. **侧车要自己写 H.265 打包**：Pion 只有解包器没有打包器，需要实现 RFC 7798（单 NAL / AP / FU 三种包）
   + SDP fmtp（`hvc1` profile-level-id 等）。工作量中等，但这是我们第一次碰非 H.264 的 RTP 打包。
3. **服务端/页面解析要重写一套**：fMP4 里 `avcC` → `hvcC`、NAL 类型表（VPS/SPS/PPS=32/33/34、
   IRAP=16~21）、关键帧判断、参数集变化重建解码器。这块我们踩过坑（SPS 变化导致冻屏/花屏），
   HEVC 要重做一遍同等严谨的防护。
4. **专利授权**：HEVC 有 MPEG LA / HEVC Advance / Via LA 三个池，商用分发需评估；
   H.264 的池更成熟、更便宜。我们是"送 ffmpeg 二进制 + 自己实现打包"，专利风险要法务确认。
5. **收益不一定有标准那么大**：我们的内容是桌面 UI（大量文字/色块），且码率不紧；
   实测可能只有 10~20%，甚至某些场景（大量细碎文字）HEVC 的"平滑"倾向会让文字显得更糊。**必须实测。**
6. **回退成本**：改的是端到端链路，出问题回退要能"一次配置切回 H.264"，所以要设计成
   `codec=hevc` 灰度开关 + 服务端/页面双端能力协商，而不是硬替换。

## 四、建议路线

| 阶段 | 内容 | 产出 | 风险 |
|---|---|---|---|
| **P0（现在做）** | 重编 slim ffmpeg（+hevc_nvenc+hevc parser/decoder）→ 用同一段抓屏做 H.264 vs HEVC 离线 A/B | 我们的真实码率/关键帧/画质（PSNR）对比 | 低（不碰生产） |
| P1 | 侧车 H.265 打包 + SDP；服务端 hvcC/IRAP；页面 HEVC 解码；能力探测与回退 | `?codec=hevc` 可跑的灰度链路 | 中 |
| P2 | 手机实测（Android Chrome / WebView）+ 弱网对比；决定是否默认 | 真机数据 + 默认值 | 中 |

**P0 的判据**（不达标就不做 P1）：
- 同画质下码率省 ≥20%，或
- 同码率下 PSNR/文字清晰度有可感知提升，且
- 关键帧体积再降 ≥20%

## 五、P0 实测结果（2026-11-12 19:0x，同一段抓屏）

**做法**：用重编的 ffmpeg（`D:\build\ffmpeg-hevc.exe`，7.0MB，含 hevc_nvenc/hevc 解码/rawvideo/mov）
把**同一段抓屏**（1920x1200@30fps，3 秒 90 帧，动态测试画面）分别用 H.264 与 HEVC 编码，
再解码回 yuv420p，用 `release-tools/psnr-y.mjs` 逐帧算 Y 平面 PSNR（参考帧完全一致）。

### 1）等码率画质（低延迟 CBR，GOP 15，bf=0，preset p1/ull）

| 码率 | H.264 PSNR(Y) | HEVC PSNR(Y) | HEVC 增益 | 文件大小 H.264 / HEVC |
|---|---|---|---|---|
| 8 Mbps | 38.83 dB | **40.08 dB** | **+1.25 dB** | 3.16 / 3.23 MB |
| 20 Mbps | 44.77 dB | **46.00 dB** | **+1.23 dB** | 7.59 / 7.77 MB |

> 按"1 dB ≈ 20% 码率"的常用换算，**等画质约省 20~30% 带宽**；与标准说法一致，但没到 40%。

### 2）关键帧 / 突发（1920x1200@120fps 20Mbps，动态画面，5 秒）

| 变体 | 码率 | 单帧 p99 | 单帧 max | >300KB 帧 | 关键帧 max |
|---|---|---|---|---|---|
| `base` H.264 无渐进刷新 | 19.6M | 365KB | 392KB | 9 | 392KB |
| `piri60_0.5` H.264 + 渐进刷新 | 19.7M | **109KB** | 209KB | **0** | 209KB |
| `hev` HEVC 无渐进刷新 | 20.7M | 332KB | 413KB | 9 | 413KB |
| `hevi` HEVC + 渐进刷新 | 20.2M | 127KB | 243KB | **0** | 243KB |

**结论**：等码率下 **HEVC 的关键帧反而略大**（413 vs 392KB）——关键帧体积由码控决定，不随编码器变好；
HEVC 的收益体现在"同样的体积画质更高"。渐进刷新对两者都有效（都把 >300KB 压到 0）。

### 3）一个坑（记下来，别再用）

**别用 `-rc vbr -cq 22` 做跨编码器对比**：实测 H.264 37.2Mbps vs HEVC 36.1Mbps（只差 3%），
但同码率 PSNR 明明 HEVC 高 1.25dB —— 因为 NVENC 的 CQ 语义在两种编码器之间不可比。
跨编码器对比必须"等码率比 PSNR"或"等 PSNR 比码率"。

### 4）编码吞吐

120fps 实时编码（5 秒素材 5.4 秒编完，与 H.264 相同）——HEVC 没有带来编码吞吐损失。

# 附录：HEVC P1 交接（2026-11-12 晚，新会话从这里开始）

## 0. 当前基线（开工前先确认这三件事）

- **已发布**：v1.0.22（Gitee release id 1302196 / GitHub id 442919791 / 官网三页 / tag v1.0.22），发布版 96,851,639 B，SHA256 `0A5543FDD1891DD174C44C61BEBC6B8B7C9AB59E518EA1388DECDF5EA9BFAF77`。
- **生产**：`%LOCALAPPDATA%\PhoneAccess` 运行的就是 1.0.22 代码（page 2026-11-13.4 / screen-server 含 `/h264-quality` 的 req/auto/caps）。
- **画质默认**：全自动（120fps / 20Mbps 起步），可用 4 个 pill 选 `全自动 / 帧率自动 / 码率自动 / 全手动`；自动调整不落盘。

## 1. P1 目标（一句话）

在**不动 H.264 默认路径**的前提下，加一条可开关的 HEVC 通路：`codec=hevc` 时服务端用 `hevc_nvenc` 编码 → 侧车按 RFC 7798 打包 → 页面 WebCodecs 解 hvc1；任何一环不支持或失败，**3 秒内自动退回 H.264**，用户无感。

## 2. 四个改动点（按依赖顺序）

| 步骤 | 文件 | 具体做什么 |
|---|---|---|
| ① 侧车打包 | `app/rtc-h264/*.go`（Pion v4.2.26） | `pion/rtp` 有 `H265Depacketizer`、**没有 H265Payloader** → 自己实现：VPS/SPS/PPS(32/33/34) 单 NAL 单独成包（S=1）、IRAP(16~21) 分片按 FU（`PayloadHdr` + `FU header`，S/E 位）、AP 可先不做；`MediaEngine` 已注册 `MimeTypeH265`，SDP 记得带 `sprop-vps/sps/pps`、`profile-level-id`、`level-id`、`tier-flag` |
| ② 服务端编码 | `app/screen-server.mjs` | `h264GopArgs(fps)` 扩展成 codec-aware：`hevc_nvenc -tag:v hvc1 -profile:v main -bf 0 -g round(fps*irMs/1000) -intra-refresh 1 -forced-idr 1 -force_key_frames`（**先用 D:\build\ffmpeg-hevc.exe 实测 hevc_nvenc 是否支持 intra-refresh**，不支持就退回"每 irMs 强制 IDR"） |
| ③ 服务端解析 | `app/screen-server.mjs`（`h264ExtractSamples/h264ParseMoov`） | 新增 hvcC 分支：moov 里找 `hvcC`（替代 avcC），取 VPS/SPS/PPS；NAL 类型判定改 `(b>>1)&0x3f`，关键帧 = 16~21（优先 19/20），参数集 = 32/33/34；`/h264-status` 的 `kf` 统计沿用 |
| ④ 页面解码 | `app/page.mjs` + `app/wc264-worker.js` | worker 认 hvcC → 组 `VideoDecoder` 的 `description`（hvcC 原样，或按 ISO 14496-15 组 box）、`codec: 'hvc1.1.6.L120.90'`（从 hvcC 推更稳）；关键帧判定同上；`__hevcCap` 探针已有，用它做门禁：`wc && hw` 都真才允许 hevc |
| ⑤ 灰度开关 | `app/product.config.json` + 页面 | `screen.h264.codec: "h264"`（默认）| `"hevc"`；页面 `?codec=hevc` 或服务端配置；**切回 h264 必须是一行配置的事**，不许改代码 |

## 3. 验收标准（P1 通过 = 全部满足）

1. **画质收益**：手机（APK + 浏览器）在 `codec=hevc` 下，等码率 Y-PSNR 比 H.264 高 ≥1.2dB（离线 enc-ab 已测 +1.25dB，线上用同场景截图抽查即可）。
2. **流畅度不回退**：120fps 档 2 分钟，解码 ≥118fps、画出 ≥100fps（`/wc264-diag` 的 `decHz/drawnHz`）、PLI ≤5、关键帧 ≤130KB、缓冲 ≤30ms。
3. **兜底**：把 `codec=hevc` 强开在一台不支持 HEVC 的设备上 → 3 秒内退回 H.264、黑屏 ≤2 秒、日志有明确原因；H.264 路径跑原有回归（`release-tools/run-suite.mjs`、`pacertest.mjs`、`recovery-test.mjs`）全过。
4. **包**：ffmpeg 换成含 HEVC 的精简版（先看体积：当前 4.32MB，`D:\build\ffmpeg-hevc.exe` 7.3MB；能裁到 6MB 以内更好）；双包审查 27/25 仍全过（强特征扫描 0）。
5. **默认仍是 H.264**；HEVC 只在显式开关下启用。

## 4. 已知风险（按优先级）

1. **Android WebView 的 WebCodecs HEVC**：探针报 `hevc=1/1/1/1`（wc/hw/main10/rtp 都真），但没在真机跑过解码；**先在手机上用 `codec=hevc` 单路试，别再动默认值**。
2. **关键帧体积**：等码率下 HEVC 关键帧略大（413 vs 392KB），intra-refresh 能把 >300KB 压到 0；上线前必须复测 `kf.keyAvgKB/keyMaxKB`。
3. **Pion 侧车没有 H265 payloader**：这是唯一要写新代码的地方，分片边界/聚合包容易出花屏；写完先用本机 Chrome 单路 60fps 小窗验证，再上 120fps。
4. **ffmpeg 重编**：`D:\build\build-hevc.sh`（MSYS2，`MSYSTEM=MINGW64`，nv-codec-headers 要 `make install PREFIX=/mingw64`）—— 产物是可编可解的，但没有 intra-refresh 之外的验证。
5. **专利池**：商用分发前要过一遍 HEVC 授权口径（本版不评估，记在这别忘）。

## 5. 建议的会话开场

> "按 `docs/HEVC-评估-2026-11-12.md` 末尾的 P1 交接做：先做侧车 H265Payloader + SDP，再服务端 hvcC/IRAP，最后页面 HEVC 解码；默认保持 H.264，用 `codec=hevc` 灰度。每步先给验收数据再往下走。"
