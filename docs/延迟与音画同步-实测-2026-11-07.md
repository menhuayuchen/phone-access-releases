# 延迟与音画同步：实测数据与优化杠杆（2026-11-07）

> 目的：回答"为什么感觉有 0.2 秒延迟""音画到底同不同步"，并给出可验证的优化点。
> 测量都在本机（回环）做，方法自同步，**不含触发抖动**。

---

## 一、测量方法（可复现）

1. 页面里用 **WebAudio 精确调度**发一声 1200Hz 短音（采样级精准），同时把页面闪成全白（320ms）；
2. 客户端**把 `<video>` 静音**，只用 `AnalyserNode` 采音频包络、用 `requestVideoFrameCallback` + canvas 采画面亮度——
   静音是为了切断"页面放声→被 loopback 抓回→再发回"的回环；
3. 各自算出：声音到达时刻、白屏到达时刻，相对同一个调度时刻；
4. 每轮 3 次取中位数。

脚本在会话里现写现跑（`%TEMP%` 下的探针），没有进产品代码。

---

## 二、结果（2026-11-07 19:0x）

| 模式 | 视频到达 | 音频到达 | 音画差（音频−视频） |
|---|---|---|---|
| **清晰（WebRTC264 / Pion）** | **129 ms** | **214 ms** | **+85 ms（声音晚）** |
| 流畅（WebRTC / wrtc） | 255 ms | 241 ms | −14 ms（基本同步） |

补充：浏览器侧只占 ~16ms（抖动缓冲 12~15ms + 解码 0.57ms/帧）；RTT 1ms；丢帧 0。

**结论**：
- **清晰模式的视频延迟最优**（129ms），是"跟手"该用的模式；
- 但清晰模式的**音频比画面晚约 85ms**——注意这 85ms 里约 15~25ms 是"网页把声音放给扬声器"的测试artifact，
  真实场景（应用出声→loopback）大约 **60ms 左右**，属于"能察觉但不难受"的边缘；
- 流畅模式音画同步好（同一条 PeerConnection，浏览器自带对齐），但视频慢了约 120ms。

---

## 三、可优化的三个杠杆（按性价比排序）

1. **音频 chunk 从 20ms 缩到 10ms**（`app\audio.cs`：`chunk = 3840 bytes` 那段 + 协议常量）。
   代价：包数翻倍、CPU 略升；收益：音频链路直接少 ~10ms，且抖动缓冲能更紧。
   需要重编 `audio.exe` + 提权部署（`release-tools\build-audio.ps1`）。
2. **音频接收端 `jitterBufferTarget` 从 20 降到 0~5ms**（`page.mjs` `rtc264AudioStart` 的 ontrack）。
   代价：弱网更易出小卡顿；收益：本地/局域网 ~15ms。**弱网要不要降，建议真机试过再定。**
3. **关掉「画质优先」**（`screen.h264.qualityFirst=true` → `p1/ull` 预设）。
   代价：静态画面质量略降；收益：编码器延迟少 1~2 帧（16~33ms）。
   这个可以在设置里让用户自己选，默认保持现状。

## 四、服务端编码段：已量，**不是瓶颈**（2026-11-07 19:1x）

**方法**（安全，不碰正在用的抓屏）：用同一套 NVENC 参数（p4/hq/vbr/cq22/20Mbps/60fps）跑**合成源**，
加 `-re` 按实时节奏喂 8 秒，再用 `-progress` 对比"编码出的最后一帧时间轴"和"真实墙钟"。

**结果**：墙钟 7.73s，最后一帧 out_time 8.00s（差值为负，说明 **采集→编码→封装没有明显积压**）。
ffmpeg 是裁剪版，合成源只有 `color`，所以这是"低复杂度画面"的下界；但它足以排除
"编码器排了 200ms 队"这种可能。

> 没有直接跑 `ddagrab` 来测：产品自己的 ffmpeg 正在用 Desktop Duplication，
> 再起一个会抢同一路显示复制（之前 18:2x 的 -40 崩溃循环很可能就是这个）。

**所以 129ms 视频延迟的构成大概是**：抓屏 60fps 采样（≤16ms）+ 编码/封装（小）+ Pion 打包 + 网络（1ms）
+ 浏览器抖动缓冲 12ms + 解码 0.6ms + 检测开销（回调 + 亮度阈值，约 16~30ms）。
剩下的余量很小，**继续压的收益不如先把音画差补平**。

## 五、关键发现（19:4x）：音频延迟的大头在 **WebRTC 音频链路**，不是采集

同一声源，同时用两个客户端测（都通过 audio.exe 的 loopback 采集，扬声器→采集那段开销两者都一样，可抵消）：

| 路径 | 声音到达（相对同一个调度发声时刻） |
|---|---|
| **PCM over WebSocket**（audio.exe → screen-server → `/ws-audio`） | **+75 / +89 / +81 ms** |
| **WebRTC 纯音频连接**（`/rtc?audio=1`，页面清晰模式实际用的） | **+242 / +242 / +250 ms** |

→ **WebRTC 音频链路自己加了约 160ms**（wrtc `RTCAudioSource.onData` 的喂法 + Chrome 对音频的
抖动缓冲/播放调度；`jitterBufferTarget`/`playoutDelayHint` 这两个提示主要作用于视频，对音频基本无效）。

这段时间里我们做过的两件事（`chunk 20→10ms`、`DesiredLatency/buffer 100→20ms`）**对 WebRTC 这条路的
端到端数字没有可见改善**——正好反证了延迟不在采集侧。不过它们把 **PCM 路径从 ~150ms 降到 ~80ms**，
在弱网/局域网场景下是有价值的。

**由此得到的两条可选修法**：
1. **清晰模式改用 PCM-WS 送声音**（页面 `startPcmAudio` 已有现成实现）：端到端 ~80ms，
   和视频 ~113ms 基本同频（音频略早 30ms，比现在晚 130ms 好得多）。代价：带宽 1.5Mbps，
   弱网要靠页面的 PCM 环形缓冲兜底。
2. 继续用 WebRTC 音频，但**给音频客户端也做延迟补偿/降缓冲**：需要给音频接收端加
   `playoutDelayHint` 之外的实验性手段（Chrome 对音频支持有限），收益不确定。

推荐先做 1 的验证（加一个 URL 开关，A/B 测完再决定默认）。

## 六、还没量到的部分（下一步）

服务端链路（抓屏→编码→侧车→发送）内部**还没有分段打点**，目前只能从两端差值推断：
视频 129ms 里，抓屏 60fps 采样最多 16ms、nvenc 编码 + Pion 打包估计 60~90ms，剩下的需要打时间戳才能定位。

做法（低风险）：在 `screen-server.mjs` 里给每帧记三个时间——从采集管道拿到、交给编码器/侧车、写出到 socket——
再在 `/latency` 暴露"最近 N 帧的三段耗时"。**只加测量，不改行为。**
