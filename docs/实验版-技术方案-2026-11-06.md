# 轻屏实验版 · 技术方案

> 2026-11-06 · **仅自用，不发布** · 不进任何安装包 · 不触碰主线代码路径
>
> 定位：主线（v1.0.18 那套）解决"够用"，实验版解决"没见过"。
> 主线不动，实验版独立分支、独立开关、独立目录，随时可以整目录删掉。

---

## 0. 一句话

主线是**把像素传得更好**，实验版是**不再传像素**——把屏幕当成"文字 + 控件 + 结构"来传，像素只作为底图。下面所有阶段都挂在这一条主线上。

---

## 1. 定位与边界

### 做什么
- 只有自己一个用户，跑在 RTX 5070 Laptop + 自用手机上
- 允许依赖：Python、GPU、本地模型、在线 API —— 客户版的"零依赖"约束在这里全部作废
- 允许失败：每个阶段独立可弃，弃了不影响主线

### 不做什么
- 不改主线任何一条用户可见路径的默认行为
- 不发版、不打包、不改 `product.config.json` 里的 version
- 不做"给客户用"的兼容性妥协（那是以后的事，到时候按实验结论反推）

### 判断标准
只有一个：**自己用的时候会不会有"卧槽"的一下**。省 30% 带宽、省 0.2 核 CPU 这类收益，不在实验版的验收范围里。

## 2. 落点盘点：现有代码能挂在哪

### 2.1 捕获与编码（`app/screen-server.mjs`）
- `ddagrab=framerate=60:draw_mouse=0:output_idx=N` —— **注意 `draw_mouse=0`**：系统光标被剥掉了，这是 E1 的前提
- 编码参数在 line 500-511，NVENC `p1 + ull + cbr_ld_hq`，`-g 60`
- `H264_NATIVE`：宽度 ≥ 2560 时 ddagrab 直喂 NVENC（零拷贝），否则 swscale 缩放
- **关键限制**：这条管线里拿不到"编码前的原始 BGRA 帧"。ffmpeg 把帧直接吃掉了。E2 要按需抓一帧，必须另开一路（见 2.4）

### 2.2 客户端三条渲染路径（`app/page.mjs`）
| 路径 | 载体 | 能否做后处理 | 默认 |
|---|---|---|---|
| WebRTC264 | `<video>` 直接上屏 | 不能（合成器 overlay） | ✅ 主通道 |
| WebCodecs | `VideoDecoder` → canvas | **能**（有 VideoFrame） | 备用 |
| MJPEG | `<img>` | 不能 | 已退役 |

E2 的矢量文字层是**叠在视频上面的绝对定位层**，三条路径都能用，不需要改渲染路径——这是它工程量可控的根本原因。

### 2.3 输入与光标链路
- `app/input.cs` → 命名管道 `\\.\pipe\dsh-input` → 注入
- `app/input.mjs` **每 400ms** 发 `{t:'cursor'}`，注入器回 `{cx,cy}`（line 74），存在 `cursorPos` 里
- 页面侧只有 `#dot` 黄点（"点哪指哪"的手指指示器），**没有任何地方消费 `cursorPos`**
- 结论：**真光标回传已经完成了一半，缺的是频率、形状、推送和渲染**

### 2.4 现成可复用的东西
- `app/capture.cs`（30KB）：已经有单帧抓取能力，E2 的"按需抓全分辨率一帧"直接复用
- `app/input.cs`：C# 注入器，E1 的 `GetCursorInfo` 加在这里
- `page.mjs` 的 HUD 管线：已有 1s `getStats` 差分 fps/码率/缓冲，E0 的度量直接接
- `app/rtc-h264/main.go`：Pion 侧车，E5 若要加 datachannel 走这里

## 3. 实验层架构

### 3.1 目录与开关

```
app/exp/                    # 新增，实验层全部在这里
  exp.mjs                   # 服务端挂载入口（路由 / 静态资源）
  cursor/                   # E1
  ocr/                      # E2/E3
  bench/                    # E0 度量台
page.mjs 内新增 EXP 模块    # 客户端，约 400 行，独立于现有逻辑
```

- 客户端开关：URL 参数 `?exp=cursor,ocr`（多个逗号分隔），不带参数 = 实验层完全不加载，**与现在行为逐字节一致**
- 服务端开关：`product.config.json` 新增
  ```json
  "experiments": { "enabled": false, "cursor": false, "ocr": false }
  ```
  默认全 false。`enabled=false` 时 `/exp/*` 全部 404。

### 3.2 隔离与回退（硬要求）
1. 实验代码只允许**新增**文件 + 在 `page.mjs` 里新增以 `EXP.` 开头的函数，禁止改现有函数体
2. 任何实验功能异常，必须 1 秒内静默失效（try/catch + 超时 + 回退到像素），**不允许出现黑屏、卡死、无法退出**
3. `pack.ps1` 增加排除规则：`app/exp/`、`app/exp/**`、`docs/实验版*`，保证打不出包含实验代码的包

### 3.3 通信
复用服务端现有 HTTP + WS，不新建端口：
- 请求-响应 → `POST /exp/<feature>`
- 服务端推送（E1 光标，30Hz）→ 现有 WS 新增消息类型 `{type:'cursor', ...}`
- 大块数据（光标位图）→ `GET /exp/cursor/<sha1>.png`，只传一次后浏览器缓存

### E0 · 地基：开关 + 度量台

**为什么第一个做**：没有它，后面所有效果的判断都是玄学。而且要能随时关掉。

**做什么**
1. `?exp=` 解析 + 右上角小面板（列出已开实验项、各自的实时指标）
2. 客户端打点（复用 HUD 的 1s 差分，新增）：
   - 帧到达间隔分布（p50/p95/p99）、解码耗时、显示到 rAF 的延迟
   - 每项实验自己的耗时（OCR 往返、光标往返）
3. 服务端 `/exp/metrics` 返回：编码 fps、每帧字节数（`-stats` 解析）、关键帧间隔
4. `exp/bench/run.cjs`：一条命令跑 `场景 × 方案`，输出 markdown 对比表

**验收**
- `node app/exp/bench/run.cjs --scene doc --exp none,cursor,ocr` 能跑完并生成表格
- 关闭实验（不带 `?exp=`）时，与实验前同一手机、同一网络的 fps/码率/延迟三项数据差异 < 2%（证明零开销）

**风险**：几乎没有。这是纯增量。

### E1 · 真光标回传

**现状的问题**

`draw_mouse=0` 让视频里没有光标，手机端只有一个跟随手指的黄点。结果是：
- 用户在电脑前动鼠标，手机上**完全看不到**
- 电脑在跑脚本、后台加载、报错弹窗，手机上只看到画面变化，不知道"光标在哪"
- 外接鼠标场景（`page.mjs` line 2323）画的是本地假箭头，位置和电脑上的真光标对不上

**方案（四步）**

1. **注入器侧**（`app/input.cs`，约 +100 行）
   - `GetCursorInfo()` → `CURSORINFO.hCursor` + `ptScreenPos`
   - `GetIconInfo(hCursor)` → 光标位图（32×32 ARGB）+ 热点 `xHotspot/yHotspot`
   - 按 `hCursor` 句柄缓存位图，只算一次（句柄复用率很高）
   - `{t:'cursor'}` 的回复从 `{cx,cy}` 扩展为 `{cx,cy,shape:"<sha1 前 8 位>",hot:[x,y],w,h,visible:0/1}`
2. **服务端侧**（`app/input.mjs` + `screen-server.mjs`，约 +80 行）
   - 轮询频率 400ms → **33ms**（30Hz；60Hz 无必要，光标本体也就 125Hz 更新）
   - 通过现有 WS 广播 `{type:'cursor', x, y, shape, hot, vis}`
   - `GET /exp/cursor/<id>.png` 返回位图，`Cache-Control: immutable`
3. **页面侧**（`page.mjs` 的 EXP 模块，约 +150 行）
   - 新增 `#realCursor` 绝对定位元素，`<img>` + `transform: translate3d()`
   - 坐标换算复用现有 `videoSourceSize` 那套（**注意**：这正是上次触屏偏移踩过的坑，必须复用同一份换算，不能另写一套）
   - 更新用 `rAF` 批量合并，避免 30Hz 直接改样式
4. **预测收敛**
   - 维护 `target`（最近一次服务端坐标）和 `shown`（当前显示位置）
   - 每帧 `shown += (target - shown) * 0.35`
   - 可选外推：若两次采样间速度稳定，`target += v * 16ms` 提前对齐
   - 目的：30Hz 采样看起来像 60fps 连续运动，且不抖

**和现有黄点的关系**
两者共存、视觉区分：真光标 = 系统样式（箭头/I-beam/等待圈），黄点 = 手指指示器。提供一个开关"只看真光标"，因为纯触屏操作时黄点更有用。

**形状支持（先做 5 种）**
箭头（`IDC_ARROW`）、文本（`IDC_IBEAM`）、链接手型（`IDC_HAND`）、等待圈（`IDC_WAIT`/`APPSTARTING`）、调整大小（`IDC_SIZEWE/NS/NWSE`）。其余一律回落箭头。

**验收**
- 电脑上动鼠标，手机端光标跟随**肉眼无滞后感**（目标：端到端 < 40ms，30Hz 采样 + 平滑后视觉连续）
- 形状切换正确（在记事本里点一下、悬停链接、拖窗口边缘、系统卡顿时）
- 光标进出画面边缘、屏幕分辨率变化时不错位
- 关闭实验时页面行为与现在完全一致

**风险**
- 部分程序用自定义光标（游戏、某些 Electron 应用），`GetIconInfo` 拿到的位图可能是 1×1 或空白 → 回落箭头即可
- 高 DPI / 多显示器：注入器坐标是物理像素，页面换算是逻辑像素，需要按 `devicePixelRatio` 换算（现有代码里已有对应逻辑，复用）

### E2 · 矢量文字层 v0（放大不糊）

**这是整个实验版的核心。**

**现状的问题**

手机上双指放大，本质是把 1920×1200 的像素拉大。要看清三号字，得放大到 300%，此时文字是一团模糊色块。服务端切高清 crop 重传能解决清晰度，但每次缩放都要重新协商、重传、等待——而且带宽翻倍。

**核心思路**

屏幕上的字是**文字**，不是像素。服务端认出来，客户端用字体重新渲染一遍。矢量文字放大一百倍还是锐的，带宽接近零。

**流程**

```
用户双指放大（scale > 1.5）
  → 客户端立刻做像素级放大（保持现在的体验，零等待）
  → 停下 300ms 后，POST /exp/ocr
      { rect: 当前视口对应的原始画面矩形, scale }
  → 服务端：
      capture.cs 按需抓一帧全分辨率 BGRA（不走视频管线）
      → 裁剪 rect
      → OCR
      → 每行返回 { text, x, y, w, h, bg, fg, ok }
  → 客户端：
      逐行画到 #textLayer（透明 canvas 或 div）
      回填之前，用半透明背景色盖住原像素文字
  → 用户再缩放/滚动 → 移除文字层，回到纯像素
```

**关键设计：逐行置信度门控**

不是整屏增强，是**只增强能增强的行**。每行判断：
- OCR 置信度低 → 跳过
- bbox 内背景色方差大（图片、半透明、渐变、视频画面）→ 跳过
- 行高 < 8px（太小，字体估不准）→ 跳过

跳过 = 保持原像素。所以最终效果是"大部分文字变清晰，复杂区域保持原样"，不会出现穿帮。

**字体与颜色**

- 字号：`bbox.height * 0.78`（经验值，需要实测调）
- 字体族：中文 `"Microsoft YaHei", "PingFang SC", sans-serif`；英文 `"Segoe UI", Arial`
- 颜色：从 bbox 内像素取**前景主色**（离背景色最远的那个聚类中心）和**背景主色**（出现最多的颜色）
- 字重：粗体检测（笔画宽度 / 行高 > 阈值）→ `font-weight: 600`

**OCR 引擎选型（做两个，二选一）**

| 方案 | 精度 | 速度 | 依赖 | 推荐 |
|---|---|---|---|---|
| **RapidOCR**（pip + onnxruntime，模型 15MB） | 高（中文屏幕文字很稳） | 区域 100–300ms | Python | ✅ 首选 |
| Windows.Media.Ocr（WinRT，C# 直调） | 中 | 最快（< 50ms） | 零 | 备选 |

自用场景直接上 RapidOCR。`product.config.json` 里已有 `runtime.pythonPath`，接得上。

**第一版刻意不做的事**

- 不做滚动时的实时增强（只做"停下才增强"）
- 不做重排（reflow）
- 不做非文字的 UI 元素（按钮、图标保持像素）
- 不做跨帧跟踪

**验收**
- 手机上看代码/文档/网页，双指放大 3×，文字边缘锐利、无锯齿
- 客观指标：把增强后的手机截图再做一次 OCR，字符准确率 **≥ 98%**；同一位置不增强的像素放大图，准确率作为基线对比
- 从手势结束到文字变清晰 **< 500ms**
- 任何失败（OCR 超时、返回空、Python 挂了）→ 没有任何视觉异常，只是"没变清晰"

**风险**
- 字体不一致会有"字对了但字形略不同"的观感 → 第一版接受，只求可读
- 对齐抖动（文字层和视频层差几像素）→ 用整像素对齐 + 放大倍数整数化规避
- RapidOCR 首次加载模型 ~2s → 服务端预热，别在请求时才加载

### E3 · 实时翻译叠加

**依赖 E2 的 OCR 结果，几乎是白送的。**

**做什么**
- 按钮"翻译这屏" → 全屏 OCR → 每行送翻译 → 译文覆盖在原位置
- 两种呈现：替换原文（原位）、或悬浮译文块（保原文可读）
- 翻译源：先用在线 API（DeepSeek / 阿里），延迟 200–800ms 可接受
- 失败降级：翻译失败就只显示原文增强（E2 的效果），不报错

**验收**
- 英文文档、英文软件界面、日文游戏 UI 三种场景下，译文位置正确、不重叠、可一键关闭
- 全流程（按按钮到译文出现）< 3s

**风险**
- 长文档一次翻译 token 量可能较大 → 分批，每批 20 行
- 代码里的英文标识符会被误翻 → 加"连续下划线/驼峰跳过"规则

### E4 · 语义问答

**分两条独立的路，都不依赖视频链路。**

**E4a · 手机本地（不出设备）**
- `<canvas>` 截当前帧 → 本地 OCR（不走服务端）→ 文字交给手机上跑的 1.5B 量化模型（Chrome Android WebGPU + WebLLM）
- 用途："这报错什么意思""帮我总结这一页""这段代码干什么的"
- 收益：隐私干净、无网络往返，是个好故事
- 风险：首次加载模型 30–60s、手机发热、WebGPU 在部分机型上被禁用 → 都必须能优雅失败

**E4b · 服务端 VLM（更强）**
- 服务端 RTX 5070（8GB）跑 2B~4B 的 VL 模型（Qwen3-VL 级别，量化）
- 截图 → 模型 → 自然语言回答
- 顺带能长成"语音指哪打哪"：截图 + "点那个红色关闭按钮" → 模型给坐标 → 注入点击
- 这是 computer-use agent 的前身，但**第一版只做"回答问题"，不做自动操作**

**验收**
- E4a：模型加载 < 60s，一问一答 < 5s，回答在 70% 情况下有用
- E4b：给定截图 + 明确的界面描述，定位坐标命中率 > 80%

**风险**：E4b 的模型选型和显存（8GB 很紧）需要先试跑，可能降级到 2B。

### E5 · 研究项（不排期，想到就试）

| 想法 | 为什么放这里 |
|---|---|
| **AI 超分（WebGPU）** | 对文字会**脑补出错误字形**，远程办公里看错数字是致命的。只能当"赏画质"的实验，不能进主链路 |
| **文档重排（reflow）** | E2 的自然延伸，但工程量是 E2 的 3 倍，等 E2 跑顺了再说 |
| **传输前 AI 打码** | 自动识别密码框/证件/聊天区域并模糊。有产品故事，但自用暂时没有强需求 |
| **自适应 jitter buffer** | 现在固定 20ms。用 `getStats` 的 `jitter`/`framesDropped` 闭环调 `jitterBufferTarget`。稳，但收益是"更稳"而不是"惊艳" |
| **ULPFEC / 重传优化** | 弱网下更抗丢，但你现在实测已经够好 |
| **光流插帧 / 120Hz** | **明确不做**：屏幕内容是静态文字 + 光标，插帧会让文字重影。插帧只对连续运动画面有意义，而这个产品的画面大部分时间不是连续运动 |

## 5. 度量台设计

### 指标（每个方案都要出）
| 指标 | 采集点 | 意义 |
|---|---|---|
| 端到端延迟 p50/p95/p99 | 服务端帧时间戳 → 客户端显示 | 主指标 |
| 帧间隔方差 | 客户端 rAF 差分 | 顺滑度 |
| 码率 / 每帧字节数分布 | 服务端 `-stats` | 带宽 |
| **文字可读性（OCR 复识准确率）** | 手机截图 → 二次 OCR | **E2 的验收指标，比肉眼可靠** |
| 功耗/温度 | 手机降频检测（fps 掉速） | 长时间可用性 |
| 实验自身开销 | 各实验模块计时 | 防止"为了炫技变卡" |

### 场景素材（固定，可复现）
1. **文档**：Word/PDF 中文正文 + 小字注释
2. **代码**：VS Code 深色主题 + 大段代码
3. **网页**：滚动新闻/表格
4. **动态**：视频播放窗口
5. **静态**：桌面壁纸 + 图标

每个场景固定一段 30s 操作脚本（滚动、放大、点击），保证 A/B 可比。

## 6. 风险与红线

1. **绝不改主线路径**。实验代码只能新增，不能改现有函数体。发现"必须改现有逻辑"时，改成"新增一个开关分支"，而不是替换。
2. **任何实验必须能一秒关掉**，且关闭后与现在行为逐字节一致（E0 验收项）。
3. **不发版**。不发 GitHub、不 build-sfx、不动 version。
4. **打包必须排除**。`pack.ps1` 加排除规则是 E0 的一部分，不是最后补。
5. **触屏坐标是雷区**。E1 的光标换算必须复用 `videoSourceSize` 那一份，另写一套必然重演 2026-11-06 的触屏偏移事故。
6. **`draw_mouse=0` 不能动**。E1 依赖它在视频里没有光标；如果哪天改回 1，手机端会出现"两个光标"。

## 7. 明确不做的事

| 不做 | 理由 |
|---|---|
| 4:4:4 / 10bit / HDR 编码 | 手机端解码是死路（H.264 4:4:4 无硬解，软件解码发热）。这也反过来证明了 E2 语义层路线是对的方向 |
| 注入游戏 DX 层做 DLSS | 反作弊、兼容性、维护成本爆炸 |
| 神经编解码（DCVC 等） | 不实时 |
| 传输层重写（QUIC/WebTransport/MoQ） | WebRTC 实测已经很好，重写是"为了优雅"不是"为了效果"。等 E1–E4 都跑顺了再评估 |
| 光流插帧 | 屏幕内容插帧会重影（见 E5 表） |
| 多路径传输 | WebTransport 单路径，要自己做只能上原生 App，代价与"主攻浏览器"冲突 |

## 实施记录

### E1 · 电脑真实光标（2026-11-07 已完成并部署本机）

分支 `exp/semantic-layer`。实际改动比预估小，因为发现注入器**早就在回报坐标**，缺的只是形状、频率和推送。

| 文件 | 改动 |
|---|---|
| `input.cs` | `cursor` 回复扩展 `cs`（形状 id）+ `vis`（是否可见）；新增 `GetCursorInfo` + 用 `LoadCursor` 句柄比较识别 14 种标准光标 |
| `input.mjs` | 轮询 400ms → **33ms**；`cursor()` 返回 `{x,y,s,v,at}` |
| `screen-server.mjs` | 新增 `/ws-exp`（30Hz 推 `{t:'cur'}`，位置没变不重发）；**必须挂在 `attachAudioWs` 之前**（后者会销毁白名单外的 socket）；audio 白名单加 `/ws-exp` |
| `page.mjs` | 实验层（只有 `?exp=` 才加载）：`#expCursor` + 12 个内联 SVG 光标 + 每帧 `toPage()` 重算 + 0.45 lerp 平滑 |
| `product.config.json` | 新增 `experiments{enabled,cursor,ocr}`，`enabled=false` 时 `/ws-exp` 直接 404 |

**验证结果（都是实测）**

- 注入器自测：回复含 `{cx,cy,cs,vis}`，实测拿到 `cs=progress`（真实光标形状）
- `/ws-exp` 鉴权：正确密钥推送正常，错误密钥 **403**
- 坐标换算：`/input` 设点 → 注入器回读，`(100,100)`、`(1280,800)`、`(2400,1500)`、`(640,1200)` **delta 全为 0**
- 页面渲染：`#expCursor` 的 `getBoundingClientRect()` 与 `toPage(1280,800)` 一致，只差 1.3px（SVG 热点偏移，符合设计）

**踩到的三个坑**（都写进代码注释了）

1. **模板字符串里的 ${** —— `page.mjs` 整页是 `String.raw` 模板，连注释里出现"美元花括号"都会让整页语法炸掉。改完已确认全文该序列计数为 0。
2. **`videoSourceSize()` 首帧前返回 16×9 占位** —— 原来只在收到消息时算一次坐标，画面就绪前光标会算到屏幕外。改成**每帧用原始屏幕坐标重算**，顺带让窗口 resize 和画面缩放都自动跟随。
3. **桌面浏览器打开本页会形成反馈循环** —— 真实鼠标移动 → 页面发 `move` → 服务端动光标 → 又触发 mousemove。测坐标时必须先点掉「控制」按钮，否则读数全错。真机触摸不受影响（触摸是绝对坐标）。

**附加开关：只看真光标（同日追加）**

页面左下角多了一个「真光标」按钮（`#expDotBtn`，**只在 `?exp=cursor` 时创建**）。点一下就把跟随手指的黄点 `#dot` 和外接鼠标的箭头 `#mcur` 都藏起来，画面上只剩电脑上的真实光标；再点一下恢复。

- 实现：`body.expNoDot #dot, body.expNoDot #mcur { display:none !important }`。
  **必须 `!important`**：主线是直接改 `dot.style.display` 的内联样式，普通样式表规则压不住内联样式（实测：手动把 `display` 设成 `block`，computed 仍然是 `none`）。
- 状态存 `localStorage['pa.exp.nodot']`，刷新后保持。
- `z-index: 9999` —— 全屏时 `#stage` 是 9996，比它低按钮会被盖住。
- 只影响显示，不影响输入：黄点只是指示器，点击照常发到电脑。

**形状修正（用户第一条真机反馈：「光标看起来很奇怪」）**

根因是**所有形状共用 `viewBox="0 0 16 16"`，而箭头路径画到了 y=19.6** —— 底部直接被裁掉，手机上看到的是个缺了尾巴的怪箭头。不是审美问题，是尺寸写错了。

修法：

- 每个形状自带 `w`/`h`（如箭头 16×22、I 形 12×18、等待 16×16），`paint()` 按各自尺寸生成 SVG，不再裁剪。
- 顺手重画了三个形状：`hand`（原来的三根线 + U 形手掌像叉子）、`sizeall`（原来描边太粗糊成一团，改成十字 + 四个实心三角）、`cross`（描边调细）。
- 尺寸：`K = 1.1`（每 viewBox 单位 → 屏幕像素）。箭头实际显示 17.6×24.2。
- **跟随画面缩放**：`frame()` 里检测 `view.scale` 变化就重画一次尺寸 —— 用户反馈"放大画面后光标大小不一样"，现在光标像贴在画面上，跟着一起放大。

调形状用的预览页：`docs/exp/cursor-preview.html`（12 个光标 3× 放大、深浅底各一行），改形状直接开它看，不用部署。
