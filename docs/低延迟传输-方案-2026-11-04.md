# 低延迟传输方案：从 TCP WebSocket 到 UDP（2026-11-04）

## 现状

- 画面：ffmpeg（NVENC）→ fMP4 → 解析成逐帧 H.264 → **TCP WebSocket** → 手机 WebCodecs 解码 → `<video>`（GPU 合成）；
- 编码已零延迟档（NVENC zerolatency/CBR/lookahead 0），客户端只渲染最新帧；
- 剩余延迟主要来自 **TCP 的队头阻塞与重传**：跨外网丢包时，后面的帧要等前面重传，体感就是"操作跟手、画面慢一拍"。

## 目标

把视频帧从 TCP 换到**不可靠、无序的 UDP 通道**：丢帧不重传、迟到帧直接丢，保时序优先。

## 方案比较

| 方案 | 原理 | 工作量 | 风险 |
|---|---|---|---|
| **A. WebRTC DataChannel**（推荐先做） | 复用 `@roamhq/wrtc` 建 PeerConnection，开 `ordered:false, maxRetransmits:0` 的 data channel；帧按 `[头 9B][H.264]` 发送；页面 `RTCDataChannel.onmessage` → WebCodecs | 1–2 天 | SCTP 消息大小（帧约 30KB，需分片）、每观众一个 PC、ICE 走 tailnet 直连 |
| B. WebTransport(HTTP/3) | 浏览器原生 WebTransport，UDP/QUIC | 3–5 天 | 需要 TLS 证书 + HTTP/3 服务端（Node 无内置，需第三方库），自签证书浏览器不认 |
| C. 自定义 UDP + FEC | 自己写 UDP + 前向纠错 + 重排 | 1 周+ | 最大，但最可控；浏览器无法直接收裸 UDP，仍需 WebRTC/WebTransport 中转 |

**结论：先做 A**，保留现有 WS 作为回退（WebRTC 协商失败/老浏览器时自动回落）。

## A 的落地步骤

1. 服务端：`/h264-rtc` 信令（offer/answer，复用现有 `/rtc` 的鉴权与 sourceAllowed）；
   - 每个观众一个 PC；`createDataChannel('frames', {ordered:false, maxRetransmits:0})`；
   - 复用现有 fMP4 解析结果，把每帧 `[cts/key/size][data]` 写入 channel；>16KB 的帧分片发送并在头部加总长/序号。
2. 页面：`if (RTCPeerConnection && VideoDecoder)` 优先走 RTC，否则回落 WS；
   - 收到帧 → `EncodedVideoChunk` → `VideoDecoder` → `<video>`（同现有渲染路径）。
3. 自适应：按 `getStats()` 的丢包/抖动调整码率（手动设置仍优先）。
4. 测试：同网 / 跨外网（Tailscale 直连、中继）各测一轮，记录 fps、延迟体感、丢包恢复。

## 验收标准

- 跨外网：画面延迟比 TCP 版再降 ≥60ms，弱网不再"越等越慢"；
- 丢包 1–3% 时能继续播放（丢帧不卡死）；
- 协商失败自动回落 WS，不影响现有功能。

## 暂不做

- GPU 零拷贝采集：当前 ffmpeg 构建的 d3d11/cuda 滤镜链不兼容，需换构建或自研采集，成本高；
- MJPEG 服务端死代码清理：等传输方案稳定后统一做。
