## A. 功能性问题（确实没做好）

### A1. 〔已更正两次〕关于「抓屏宽度改不动」

**这一条我最初写错了，第一次更正又写歪了一半，这里给出最终版本。**

**最初写的**："`capture.mode` 里 `width=1440`，说明抓屏宽度卡住"。

**第一次更正（错的）**：说"`capture.mode` 的 `width` 只是切换窗口/显示器目标用的，**不是**实际抓屏宽度，
真实宽度只来自 `capture.exe` 启动参数"。

**最终结论（2026-10-29 读代码 + 实测确认）**：这个字段**会真的决定抓屏宽度**。
`capture.cs` 的抓屏循环里是：

```csharp
int wantW = ctlWidth > 0 ? ctlWidth : targetWidth;   // ctlWidth 就是从 capture.mode 的 width= 读进来的
int outW  = Math.Max(2, Math.Min(wantW, screen.Width));
RunPipeline(screen, outW, outH);
```

也就是说：`capture.mode` 的 `width > 0` 时**覆盖**启动参数里的 targetWidth；等于 0/缺省时才用 argv。
所以"它停在 1440"确实会让画面变 1440 宽——不是模型文件，是真实控制量。

**为什么实测时看起来"没坏"**：`screen-server.mjs` 的 `publishViewers()` 每 700ms 会把
`sourceState.width`（= `CAP_W`，按物理分辨率/`maxCaptureWidth` 算出来）写回 `capture.mode`，
`capture.exe` 下一轮 `ReadControl()` 就把它改回来。所以稳态下两边一致（当前实测
`capture.mode` = `mode=mjpeg monitor=-1 window=0 width=2560`，与 `CAP_W` 相同）。

**实测（2026-10-29）**：

```
capture.exe 命令行: ... 2560 40 ...        ← 宽度 2560、间隔 40ms
screen-server 参数: "2560x1600"
capture.mode:      width=2560              ← 与 CAP_W 一致
health: in=24.5 out=24.0 cap=33
```

**所以「画面质量」设置是有效的**：写配置 → 完整重启 → `capture.exe` 拿到新的 argv，
同时 `capture.mode` 也会被服务端写成同一个值。

**我犯的错**：先拿一个残留的"模型文件"当运行状态（第一次），又反过来断言那个字段无关紧要（第二次）。
两次都是**没读到真正消费它的那行代码**（`capture.cs:708`）。这条字段的耦合已在
`screen-server.mjs` 的 `writeMode()` 上写明，避免下次再猜。
### A2. 帧率上限由 CPU 决定，没有优化手段

- 2560×1600 实测 18–24 fps（CPU 决定，不是网络）
- `enableDsh=true` 时多一个 408MB 的 DSH web 抢 CPU，会掉到 9–18 fps
- WebRTC 配置 24 fps，实测只有 12–15（软件 VP8 编码受限）

**没有做**：硬件编码、增量帧、脏矩形传输。属于性能优化，不是安全缺陷。

### A3. `/input` 不做事件校验

`input.mjs` 的 `send(obj)` 直接 `JSON.stringify` 后写进管道，不校验 `t`/`x`/`y`/`vk`。
原生侧 `input.cs` 有 `switch (t)` 会忽略未知类型，但坐标没有范围钳制。

**评估**：`/input` 现在必须带密钥（B 组），能调它的人本来就有完全控制权，
所以校验不提升安全性，只防"页面自己发错数据"。**选择不改**是因为猜错事件 schema 会把正常操作弄坏。

### A4. DSH 复用会返回 503

`tunnel-proxy.mjs` 的 `resolveToken()` 从 `web-lan.log` 抓 `token=`。
这个日志**只有产品自己启动 `dsh web` 时才有**。如果去复用已经在跑的 DSH 桌面版，
端口对得上但拿不到令牌 → `/go` 返回 503。

**当前处理**：门只指向自己启动的 `dsh web`；`dsh-port.ps1` 只用于日志提示。
客户版 `enableDsh=false`，这个问题对客户不存在。

## B. 安全上的接受取舍（我已知，且认为可接受）

### B1. Defender 排除（2026-10-29 已收窄，原文"排除整个安装目录"已作废）

原来 `install.ps1` 把 `%LOCALAPPDATA%\PhoneAccess` 和 `%LOCALAPPDATA%\DshInput` **整个目录**
加进 Defender 排除。理由：`capture.exe` / `input.exe` 会被反复误杀。

**现在改成只排除具体可执行文件**：`capture.exe`、`capture.exe.bak`、`input.exe`、`audio.exe`、
`sources.exe`、`runtime\node.exe`，以及高权限注入器那份 `input.exe`。
安装时会**先删掉旧版本留下的两条整目录排除项**（`Add-MpPreference` 只加不减，不删等于没改）。

**代价**：仍然不扫这几个 exe 本身（误杀风险与之前相同）；但"往这两个目录里丢任意程序"不再自动免扫描。

### B2. `machine.id` 可写

许可证绑定的是机器码，而机器码缓存在 `machine.id` 里（虽然启动时会 `-Force` 重算）。
有决心的人可以伪造机器码把许可证搬到别的机器。**目标是"防随手转发"，不是"防逆向"。**

### B3. Origin 检查可被非浏览器客户端绕过

`tailscale serve` 会把伪造的 `Host` 透传上来。非浏览器客户端可以绕过同源检查。
但因为仍然需要访问密钥，风险有限。

### B4. 纯客户端许可证，无法远程吊销

没有服务器 → 没有吊销通道。到期后是"软停"（画面返回 402），程序还在。

### B5. 安装包未签名

智能屏会警告，说明书教客户点"更多信息 → 仍要运行"。**买证书能解决，但不是代码问题。**

## C. 设计上需要你判断的

### C1. `/go` 的令牌机制

`tunnel-proxy` 把 DSH 的登录令牌从日志里抓出来，拼进 `/?token=` 转发。
这是**有意的设计**（让客户端的手机不用每次扫码），但它意味着：
**能读那个日志文件的人就能拿到登录令牌**。日志在安装目录里，普通用户权限可读。

**请判断**：这个机制的信任边界是否合理？有没有更好的做法？

### C2. `/health` 的 `isLocalConn` 豁免

必须保留——`supervise.ps1` 每 8 秒无密钥探活。去掉会导致重启风暴。
现在只返回计数类字段（fps/丢帧/模式），窗口标题已按密钥过滤。

**请判断**：剩下的这些计数会不会被用来做侧信道（比如推断用户在看什么）？

### C3. `run-autostart.vbs` 与计划任务

开机自启走计划任务 + VBS 隐藏窗口。**请检查**有没有可以被非管理员利用的启动路径。

## E. 本轮修复过程中新发现（P0 修完后暴露出来的，留给下一轮）

这几条不在原修复清单里，是修 P0 时顺带查出来的，**没有修**，先记账。

### E1. 体检脚本会**执行**用户可写目录里的 exe（同类提权点，但要管理员上下文才成立）

`check-health.ps1` 会运行 `%LOCALAPPDATA%\DshInput\cursor-probe.exe`（它是用户可写目录）。
谁在**管理员**上下文里双击「自查」，谁就把那个目录里的任意同名 exe 当管理员跑了。
本机的 `DshInput` 里实测还躺着 `cursor-test.exe` / `input-diag*.exe` 等开发残留。
**缓解方向**：体检开头判断"当前是管理员就拒绝跑探针"（体检本身不需要管理员）；探针路径移出用户可写目录。

### E2. `dsh-input` 命名管道的 DACL 是 Everyone 完全访问

高权限（High）的 `input.exe` 连的是一个 `Everyone:Full` 的管道。同机**任何本地账户**都能连上它，
让 High 进程替它注入键盘鼠标。不是代码执行，但在"多本地账户 + 机主正登录"时是真实的跨用户操作面，
提权化之后影响比之前大。**缓解方向**：管道 DACL 收到当前用户 SID（`input.cs` 一处常量）。

### E3. 入口 URL（含完整密钥）会落进文本文件

`supervisor.log`（安装目录里，普通用户可读）里有完整的 `https://<域名>/?k=<密钥>`；
「自查」的输出也会把带 `k=` 的地址打印出来。与 P4-1 的 `%TEMP%` 安装日志是同一类问题：
**前提是"卖家拿不到密钥"，而密钥就明文躺在日志里**。**缓解方向**：落盘/打印前把 `k=` 脱敏。

**进展（2026-10-29）**：P4-1 已经修掉了 `%TEMP%\pa-install-start-*.log` 那条（改成先脱敏再删）；
`supervisor.log` / 自查输出这两处**还没修**——它们要改的是 `start-screen.ps1` 写日志的入口和
`check-health.ps1` 的打印，涉及面比 P4-1 大，留给下一轮。

### E4. `input.log` 没有轮转

现在只轮转 `screen-capture.log`（`supervise.ps1` 里那个 2MB 判断）。`input.log` 一直追加
（实测已 300KB+，提权模式搬到了 Program Files 里）。**缓解方向**：跟 `screen-capture.log` 用同一套轮转。
