### [x] P0-1 · H1-r1 `/manifest.json` 免密钥且原样吐出访问密钥

> **状态：2026-10-29 已修，四条验收全部实测通过。** 但**修法与清单原文有三处不同**，
> 原因是一条实测结论推翻了原文的假设，见下面的「实施记录」。

**位置**：`screen-server.mjs` 的 `/manifest.json` 路由

**根因**（三条叠加）：
1. 在 `LICENCE_OPEN_PATHS` 里、**不在** `STRICT_AUTH_PATHS` 里
2. `start_url: '/?k=' + KEY` —— 把完整密钥放进了响应体
3. `cache-control: max-age=86400`

**链路**：`https://<机器名>.ts.net/manifest.json`（serve 转发 → remoteAddress=127.0.0.1 →
命中第一层 `isLocalConn` 豁免）→ 不查密钥不放行也无所谓，因为**响应体自己带着密钥**。
拿到 `k=` 之后 `/frame.jpg`、`/stream`、`/input`、`/exec` 全部解锁。

**修法**（三处一起改，缺一不可）：
```js
// 1) 加进严格集合
STRICT_AUTH_PATHS 加入 '/manifest.json'

// 2) start_url 不带密钥（靠会话 cookie）
start_url: '/'      // 原来是 '/?k=' + encodeURIComponent(KEY)

// 3) 去掉长缓存
'cache-control': 'no-store'
```

**验收标准**：
- [x] `curl -i https://<域名>/manifest.json`（不带 k、不带 cookie）→ **401 或 403**
      → 实测 401（三个来源 IP 各测一次 + 真实域名路径；响应体不含密钥）
- [x] 手机浏览器带 `?k=` 打开页面后，页面内能正常取到 manifest（DevTools 里 200）
      → 实测 200（用真实 Chrome 156 验证，见「实施记录」第 1 条）
- [x] 手机"添加到主屏幕"流程仍能走通（装出来的 App 打开能进页面，不是 401）
      → 机制已验证（浏览器自己抓清单那一次请求拿到了 200）；**真机点"添加到主屏幕"这一下仍需手机实测**
      → **2026-10-30 真机实测（安卓/小米）果然 401「这个地址缺了钥匙」**：装的 App 不带 cookie 打开 start_url='/'。
      已修：start_url 改回 '/?k=<密钥>'（清单本身在严格鉴权集合内、裸 GET 仍 401，无新增暴露面）。详见 STATUS.md 第十二节。
- [x] 轮换密钥后，manifest 里**看不到**任何旧密钥 → 响应体里已经没有任何密钥（`?k=` 都不再出现），`start_url` 是 `/`

**实施记录（2026-10-29，与清单原文的差异）**

1. **原文第 1 条（加进 `STRICT_AUTH_PATHS`）单独做会让"添加到主屏幕"坏掉。** 实测（Chrome 156）：
   浏览器取 `<link rel="manifest">` 时**不带 cookie**——服务端记到的是空 cookie + 浏览器 UA。
   实测证据：临时实例上先只加严格集合，页面正常打开后服务端 `screen-auth.log` 记到
   `401 path=/manifest.json ua=Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36...`；
   同一页面里 `fetch('/manifest.json')`（默认带 cookie）却是 200、`fetch(..., {credentials:'omit'})` 是 401。
   → 即"cookie 在、浏览器自己的清单抓取不带"。
2. 因此补了一个**页面签发的一次性短时 token**（不是第二把钥匙）：
   `screen-server.mjs` 里 `manifestHref()` 用 `HMAC-SHA256(KEY, 'manifest|exp')` 现签 1 小时有效，
   页面渲染时塞进 `<link rel="manifest" href="...&exp=&sig=">`；`STRICT_AUTH_PATHS` 对 `/manifest.json`
   额外认这个 token。裸 GET 仍然 401（伪造 sig / 过期 exp 都实测 401）。
   token 只放行一份**不含任何秘密**的清单文档，不能当访问密钥用。
3. 原文第 3 条（`cache-control: no-store`）已做；另外给 `<link rel="manifest">` 加 `?v=2`，
   把手机上**已经缓存过的旧清单**（里面带过密钥、曾经 max-age=86400）换成新 URL。
4. 页面里的密钥（`const KEY = "__KEY__"`）保持不变——页面本来就只发给已授权请求，不属于泄露面。
5. 服务重启方式：**没有**照「六、统一验收」跑 `restart.ps1`。原因是 `stop-phone-access.ps1`
   会杀掉 `--profile web ... 8642` 进程，而**本机这次对话的网页就挂在那个进程上**
   （`DeepSeek Harness.exe --profile web --host 127.0.0.1 --port 8642`）。改成只重启
   `screen-server.mjs`（由 supervisor 6–7 秒内自愈拉起），改动文件同样生效。

### [x] P0-2 · I1 `DshInput` 目录用户可写 + Highest 计划任务 = 提权

> **状态：2026-10-29 已修（采用推荐方案 A），四条验收全部实测通过。**

**位置**：
- `install-elevated-input.ps1`（注册任务，`RunLevel Highest`，执行 `%LOCALAPPDATA%\DshInput\input.exe`）
- `supervise.ps1:324-326`（用户级守护进程 `Stop/Start-ScheduledTask` 触发它）
- `install.ps1:1484-1486`（把这个目录加进 Defender 排除）

**根因**：`%LOCALAPPDATA%\DshInput\` 由提权进程创建但 **ACL 继承自用户目录 → 用户可写**。
任何用户级恶意代码替换 `input.exe` → 守护进程或攻击者直接 `Start-ScheduledTask`
→ 以 Highest 完整性启动 → **无 UAC 拿到管理员**。而且 Defender 排除让 payload 不被扫描。

**修法**（二选一，推荐 A）：
- **A**：把注入器部署到 `%ProgramFiles%\PhoneAccessInput\`（用户不可写）
- **B**：`DshInput` 目录 ACL 收紧：`Users: 读+执行`，`SYSTEM/Administrators: 完全控制`

附带：`Add-MpPreference` 只排除**具体文件**（`input.exe`、`capture.exe`），不排除整个目录。

**验收标准**：
- [x] 以普通用户（非管理员）执行 `Set-Content ...\input.exe test` → **拒绝访问**
      → 用一个 `RunLevel=LIMITED` 的一次性计划任务拿真实 Medium 令牌实测：
      控制项（写 `C:\Program Files\_probe.txt`）= DENIED（证明令牌确实被过滤），
      目标目录新建文件 = DENIED，`input.exe` 的 ACL 里普通用户写权限 ACE = 0 条。
- [x] 以普通用户能正常「启动」并使用手机控制（不能因为收紧 ACL 而坏掉）
      → 实测：杀掉注入器后 supervisor 6 秒内从 Program Files 重新拉起，手机侧注入正常。
- [x] `Get-ScheduledTask 'DSH Input Injector'` 的 Actions 指向**用户不可写**的路径
      → `Execute = C:\Program Files\PhoneAccessInput\input.exe`、`WorkingDirectory` 同目录、
      `Arguments` 里的日志也在同目录。
- [x] 注入功能实测仍可用（手机点一下，光标真的动）
      → `POST /input` 发 `move (x+4,y+4)`，`/cursor` 读回正好 `+4/+4`，再移回原位（High 完整性日志行
      `input service start pipe=dsh-input integrity=high`）。

**实施记录（2026-10-29）**

按审计结论，**不止搬 exe**，整条"提权进程碰得到的路径"都搬走了：

| 东西 | 原来 | 现在 | 理由 |
|---|---|---|---|
| 注入器 exe | `%LOCALAPPDATA%\DshInput\input.exe` | `%ProgramFiles%\PhoneAccessInput\input.exe` | 用户可写 → 用户不可写（Users 只有 `(RX)`，实测 `icacls` 无写 ACE） |
| 提权进程日志 | `%LOCALAPPDATA%\PhoneAccess\input.log`（安装根，用户可写） | `%ProgramFiles%\PhoneAccessInput\input.log` | 提权进程往用户可写路径追加文件 = 把受保护文件的写入权送出去 |
| 任务的 `WorkingDirectory` | 安装根（用户可写） | Program Files 目录 | 同上，去掉 CWD 相对路径/搜索面的隐患 |
| `elevated.enabled` 标记 | `%LOCALAPPDATA%\DshInput`（用户可伪造） | Program Files 目录（只有管理员能造） | 判定"是不是提权模式"改以**任务 Action 路径**为准，标记只作辅助 |
| install transcript | `%LOCALAPPDATA%\DshInput\install.log` | Program Files 目录 | 随日志一起搬 |

其它配套改动：
- `start-screen.ps1`：提权模式下**不再**往 `DshInput` 部署副本（不然每轮守护都会把清理掉的旧副本复活）；
  任务指向不是 Program Files 的旧状态会打警告并回退到普通权限启动（拒绝使用可被替换的提权 exe）。
- `supervise.ps1`：`Stop/Start-ScheduledTask` 失败不再 `-ErrorAction SilentlyContinue` 静默吞掉，改为写日志。
- `check-health.ps1`：注入器路径与 `input.log` 都按**当前模式**取（这条最容易引入静默回归）。
- `selfcheck.ps1`：`Test-SelfElevated` 增加"任务是否装在用户能改的目录"断言，旧装法会报 warn。
- `uninstall.ps1`：连 Program Files 目录一起删，Defender 排除项也按新前缀撤销。
- `install.ps1`：Defender 排除从"整个目录"改成"具体 exe"，并**先删掉旧的两条整目录排除项**
  （`Add-MpPreference` 只加不减，不删等于没改）；第 8 步成功判定从"标记文件存在"改成
  "任务 Action 真的指向 Program Files"。
- 普通权限回退路径原样保留：非提权模式下 input.exe 仍在 `DshInput` 里跑在**同一完整性级别**，
  不跨越权限边界，不构成提权（能替换它的人本来就已经拥有该用户的代码执行能力）。

**验证过程中确认的两件事（对后续维护有用）**
1. 普通权限 `Stop-ScheduledTask` / `Start-ScheduledTask` 这个 `RunLevel=Highest` 任务**都能成功**
   （Limited 令牌实测 OK）——`supervise.ps1` 的自愈路径成立，不需要额外授权或 COM 改 DACL。
2. **不需要**给 Program Files 目录手工设 ACL：提权身份新建目录时继承的默认 ACL 就是
   `SYSTEM:F / Administrators:F / Users:(RX)`。`install-elevated-input.ps1` 里只做**只告警**的自检。

## 五、P4 · 低危残留（知道就行，可延后）

### [x] P4-1 · `%TEMP%\pa-install-start-*.log` 可能留密钥 URL

> **状态：2026-10-29 已修（改成"先脱敏再删"）。**

**根因**：安装失败时清理不完全，日志里可能带完整 `?k=` URL 留在磁盘
**修法**：拿到启动脚本的输出后**立刻**把 `k=<十六进制>` 换成 `k=<已脱敏>`，再走原来的
"删 5 次、删不掉就写空文件"流程。这样即使安装被杀死在"写完日志、还没删"之间，
磁盘上留下的也是脱敏后的内容。
**验收**：`Select-String "$env:TEMP\pa-install-start-*.log" -Pattern 'k=[0-9a-f]{8}'` → 无匹配
→ 当前 `%TEMP%` 里本来就没有这类残留文件；脱敏正则已实测：
`http://<本机Tailscale地址>:8660/?k=43ed48b48f6f3d...` → `...?k=<已脱敏>`

### [x] P4-2 · `uninstall.ps1` 按进程名杀

> **状态：2026-10-29 已修（改成按可执行文件所在目录杀）。**

**根因**：`Stop-MatchingProcess -NamePattern '^input\.exe$'` 会误杀系统上同名无关程序
**修法**：不再按进程名，改成"**可执行文件路径落在本产品的三个目录里**"才杀
（安装根 / `%LOCALAPPDATA%\DshInput` / `%ProgramFiles%\PhoneAccessInput`）。
没有照抄 install.ps1 那种"命令行含安装目录"的写法：提权注入器的命令行是
`dsh-input "C:\Program Files\PhoneAccessInput\input.log"`，不含安装目录，会漏杀。
**验收**：本机 dry-run 命中的进程恰好是产品自己的 7 个（audio / capture / input / 4 个 node），
没有误伤同名程序。

### [x] P4-3 · 安装报告里 tailnet 裸 IP 未脱敏

> **状态：2026-10-29 已修。**

**根因**：`Get-SafeText` 只挡 `http(s)://` 开头的内容；裸 IP 不含协议头，会原样进报告
**修法**：`Get-SafeText` 增加一条：把非回环的 IPv4 一律换成 `<IP已隐藏>`；
**127.0.0.1 保留**（诊断要用，且不指向真实地址）。
**验收**（实测）：`<本机Tailscale地址>` / `192.168.1.5` / `10.0.0.7` → `<IP已隐藏>`；
`127.0.0.1:8660` 原样保留；`https://…` 仍是"（网址已隐藏）"。

### [x] P4-4 · upgrade 未匹配路径不 `destroy` socket

> **状态：2026-10-29 已修（只改最后一个处理器，先说清楚为什么不能两个都改）。**

**根因**：两个 `upgrade` handler 对不匹配路径直接 `return`，连接悬挂占用——极低级
**修法**：这条**不能无脑给两个处理器都加 destroy**：`rtc.mjs` 的处理器先注册、只认 `/rtc`，
它要是 destroy 了，后注册的 `/ws-audio` 处理器就再也接不到连接（声音会整个坏掉）。
所以只在**最后**一个处理器（`screen-server.mjs` 的 `attachAudioWs`）里 destroy，
`rtc.mjs` 那边加注释说明为什么必须留着 `return`。
**验收**（实测，带 Upgrade 头打 4 条路径）：

| 路径 | 结果 |
|---|---|
| `/nope`（没人认领） | **19ms 就断开**（000），不再挂着 |
| `/ws-audio?k=<key>` | `101 Switching Protocols`（声音通道正常） |
| `/ws-audio`（无密钥） | `401` |
| `/rtc?k=<key>` | `101`（RTC 通道正常） |

### [x] P4-5 · `capture.mode` 的 `width` 长期不等于 `CAP_W`

> **状态：2026-10-29 查清了，**结论和清单原文相反**——这个字段**会真的决定抓屏宽度**，
> 所以不能简单删掉。已加注释 + 记账，不行为改动。

**清单原文**："目前无功能影响（真实宽度来自 argv），属模型与实际不一致"。
**实际代码**（`capture.cs:708`）：`int wantW = ctlWidth > 0 ? ctlWidth : targetWidth;`
—— `ctlWidth` 就是从 `capture.mode` 的 `width=` 读进来的，**大于 0 时直接覆盖 argv 的 targetWidth**，
再传给 `RunPipeline(screen, outW, outH)` 当作输出尺寸。也就是说：
`capture.mode` 里那个 width 不是"模型文件"，它是真的会让画面变小的覆盖值。
（这也解释了为什么它曾经停在 1440 时值得追——真写进文件就会生效。）

**当前实测**：`capture.mode` = `mode=mjpeg monitor=-1 window=0 width=2560`，与 `CAP_W` 一致。
**动作**：在 `writeMode()` 上加了注释说明这层耦合（"这里必须写真实抓屏宽，写小了画面就真的变小"），
并在 `03-已知问题.md` 的 A1 里更正了原来"该字段不是实际抓屏宽度"的说法。**没有改行为**：
`/mode` 支持客户端传 width（会被钳到 `CAP_W`），而 `publishViewers()` 每 700ms 又把它写回 `CAP_W`，
把这层语义彻底拆干净属于重构，不在本轮范围。
