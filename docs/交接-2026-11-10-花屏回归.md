## 二、两个可疑病因（按可能性排序）

### 病因 1：**100Mbps 码率也会压垮 Node 解析管道**（可能性最高）

今天加的「像素率防护」只算了 `W × H × fps`（预算 4.92 亿像素/秒），**完全没管码率**。

但实测 `1920x90 @ 100000kbps` 时：
- 每帧约 1.1 MB
- 90fps → **每秒 100MB 数据流经 Node 的 fMP4 解析器**
- 日志显示这个配置下**仍然出现 `ffmpeg exit 4294967256`**

**推断**：管道压力 = 帧率 × 分辨率 × **码率**，三者都算。像素率防护漏了码率这一维。

**验证方法**：把 kbps 降到 50000，观察 `dropped` 和 `ffmpeg exit` 是否归零。

### 病因 2：WebCodecs 解码器偶发报错（`A key frame is required`）

Worker 里 `decoder error` 回调会设 `waitKey = true` 等待下一个 IDR。GOP 是 0.5 秒，正常应该 0.5 秒内恢复。

但如果**同时** ffmpeg 在崩溃重启，IDR 可能迟迟不来 → 画面长时间花屏/冻结。

**验证方法**：在页面 console 看 `window.__wc264.stats.dropped` 是否随花屏同步增长，以及 `lastErr` 的内容。

## 四、WebCodecs 方案的关键事实（不要重复踩坑）

**数据流**：
```
RTCRtpScriptTransform -> Worker 收到【完整 H.264 编码帧（Annex-B）】
  -> 切 NALU、取 SPS/PPS、识别 IDR(type 5)
  -> VideoDecoder（必须给 avcC description + AVCC 输入）
  -> VideoFrame 回传主线程 -> Canvas 绘制
```

**四个致命坑（均已踩过并修复，不要回退）**：
1. **`frame.data` 不是 RTP 包**，是已组装的 Annex-B 整帧（`00 00 00 01` 开头）。不需要 FU-A 重组。
2. **必须用 `addEventListener('rtctransform')`**，`self.onrtctransform = ...` 属性赋值会错过事件（表现为 `on=true` 但零帧）。
3. **必须给 `description`（avcC）且输入用 AVCC**。不给 description 时 Chrome 不按 Annex-B 解析，喂 1000+ 帧一个 `VideoFrame` 都不出。
4. **关键帧必须从 NALU type 5 判断**，`RTCEncodedVideoFrame.type` 几乎总是 `delta`。
5. **不能省略 `controller.enqueue(frame)`**，否则浏览器判定断流、PC 直接被关。

**性能实测**：WebCodecs 解码 87-120fps，硬件解码 `hw=prefer-hardware` 生效。

## 五、建议的排查顺序（新会话从这里开始）

1. **先把码率降到 50000**，观察 10 分钟：
   ```powershell
   $key = (Get-Content "$env:LOCALAPPDATA\PhoneAccess\screen.key" -Raw).Trim()
   Invoke-WebRequest "http://127.0.0.1:8660/h264-quality?k=$key" -Method POST `
     -Body '{"width":1920,"fps":90,"kbps":50000}' -ContentType 'application/json'
   ```
2. **每 2 秒采样侧车 `dropped`**，看它是否随花屏增长：
   ```powershell
   Invoke-WebRequest http://127.0.0.1:9801/health | Select-Object -Expand Content
   ```
3. **在页面 console 看 Worker 统计**：
   ```js
   window.__wc264.stats   // {rtp, frames, decoded, dropped, keyframes}
   window.__wc264.lastErr // 解码错误内容
   ```
4. **如果确认是码率压垮管道**：给防护加码率维度（`kbps` 上限，比如 1920 宽最多 60Mbps）
5. **如果确认是解码器恢复慢**：缩短 Worker 里的 `waitKey` 等待（比如连续 3 个 P 帧都没 IDR 就主动请求关键帧）

## 七、必读的坑（今天又踩了一遍）

1. **改 `page.mjs` 必须重启 `screen-server`**（ESM 启动时 import 一次）
2. **PowerShell 的 here-string 里不要出现双引号**，会被当成字符串结束（git commit 用 `-F 文件` 更安全）
3. **编辑 `page.mjs` 后要用 `app/check-page-js.mjs` 验证**，`node --check` 只查模块语法、不查模板字符串里的页面 JS
4. **`taskkill` 失败会被 catch 吞掉**，重启后必须核对 PID 是否变化，否则改的代码根本没加载
5. **不要用行号偏移删大段代码**，会切掉块内的行导致语法错误（用 `edit` 工具精确替换）
