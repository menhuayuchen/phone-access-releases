# 交接：花屏回归排查（2026-11-10 上午 → 11:00 已修一轮）

## 一句话结论

**这一轮的花屏/画面不恢复，根因是 WebCodecs 接收端的解码器没跟着编码器换参数集（SPS/PPS）。**
编码器一重启（切分辨率、切窗口、ffmpeg 崩溃重启），解码器还在用旧 avcC 解新码流 ——
桌面 Chrome 上的表现是**画面冻住**（计数器全绿、没有任何报错），手机上大概率是**一整片花屏**。
已修，commit `35d18998`，生产已上线并实测。

## 一、这次修了什么（全部已实测）

| # | 文件 | 问题 | 修法 |
|---|---|---|---|
| 1 | `app/wc264-worker.js` | Worker 喂帧前把 SPS/PPS 剥掉了（走 avcC description），编码器换参数集后解码器永远发现不了 → 冻屏/花屏 | 记住解码器是按哪组 SPS/PPS 配的，比对到变化就 **关掉重建**、等下一个关键帧。实测切分辨率只丢 1 帧 |
| 2 | 同上 | 首连必丢 45 帧、黑 0.5 秒并报 `A key frame is required`：拿到 IDR 就先清 `waitKey`，再发现解码器还在 `configure`，这一帧丢掉后紧接着喂 P 帧 | `configure` 期间把关键帧存起来（`pendingKey`），配置好立刻喂；`waitKey` 只在**提交成功**后清。首连丢帧 45 → 8 |
| 3 | `app/page.mjs` | 看门狗原来"卡 3 秒就**永久**回退 `<video>`"：编码器每次重启都断帧 1~4 秒 → 每调一次画质就永久丢掉 WebCodecs；而且 `gaveUp` 置位后再卡死连回退都不做（黑屏） | 改成先**重建接收端**（最多 3 次、间隔 1.2 秒），救不回来才回退；重连时清零。另加"解码器僵死"判据（帧在进、解出来的不涨） |
| 4 | 同上 | 网络丢包时，缺参考帧的 P 帧照旧被解 → 真·花屏直到下一个 IDR | 把 `getStats().packetsLost` 增长当断链信号 post 给 Worker，Worker `waitKey=true` 等下一个 IDR（最多冻 0.5 秒，不出花屏） |
| 5 | 同上 | WebCodecs 模式下 HUD 一直显示"连接中"（`vid.videoWidth` 恒 0），排查时看不出真实分辨率 | HUD 用画布尺寸；清掉遗留报错串 |
| 6 | `app/screen-server.mjs` | 切到 2560 宽时只按宽度重新打开零拷贝路径（不看能力探测结果），这台机器上必定 `-40` 秒退两次才回退，白黑 2~4 秒，断帧还会把手机的 WebCodecs 接收端拖死 | `H264_NATIVE = H264_ZEROCOPY && …`。日志里不再出现 `ffmpeg exit 4294967256` |
| 7 | `app/rtc-h264/main.go`（第二轮，侧车 0.5.1） | 侧车/Node 丢帧时 RTP 序号不前进，接收端发现不了 → 后面 P 帧全缺参考帧、花屏到下一个 IDR | 丢帧置 `needKey` 等下一个关键帧；帧输入头加 gap 位；`/health` 加 `gapMarks`、`/h264-status` 加 `feedDrops` |

## 二、实测证据（本机 Chrome，`http://100.108.92.22:8660`）

修前（切 1920x1200 → 2560x1600）：

```
canvas 冻在 [2560,1600]      ← 画布尺寸再没变过
rtp / frames / decoded 照涨（90fps）、lastErr 空
用 invert 滤镜让整屏变一次色：<video> 的像素变了，画布的像素一个都没变 → 画布是死的
```

修后：

```
首连 1920x1200  : dropped 8（原 45）、decoded == frames、无 decode 错误、HUD 显示 1920x1200
切 2560x1600    : canvas -> [2560,1600]、cfg+1、spsChanges+1、只丢 1 帧、invert 测试=live
切回 1920x1200  : canvas -> [1920,1200]、cfg+1、只丢 1 帧、live、81fps / 15.6Mbps / 缓27ms(WC)
```

**复现/验收方法**（页面 console，或 `dsh_browser_execute`）：

```js
// 1) 画布是不是活的：整屏反色 1 秒，比较画布像素哈希有没有变
const sig = el => { const c=document.createElement('canvas'); c.width=32;c.height=20;
  const g=c.getContext('2d',{willReadFrequently:true}); g.drawImage(el,0,0,32,20);
  const d=g.getImageData(0,0,32,20).data; let h=0;
  for(let i=0;i<d.length;i+=4) h=(h*31+d[i]+d[i+1]*7+d[i+2]*13)%2147483647; return h; };
const cv = window.__wc264.canvas; const a = sig(cv);
document.documentElement.style.filter='invert(1)'; await new Promise(r=>setTimeout(r,1000));
const b = sig(cv); document.documentElement.style.filter='';
console.log('画布活不活', a!==b, 'cfg', window.__wc264.cfg, 'spsChanges', window.__wc264.spsChanges);

// 2) 切分辨率（等价于手机上改画质/切窗口）
fetch('/h264-quality',{method:'POST',headers:{'content-type':'application/json'},
  body:JSON.stringify({width:2560})});
```

`window.__wc264.stats` 新增字段：`cfg`（解码器配置次数）、`spsChanges`（参数集变化次数）、
`queue`（`decodeQueueSize` 积压）、`gaps`（丢包断链次数）。

## 三、上一份文档里被证伪的推断（别再照着查）

1. ~~"100Mbps 码率压垮 Node 解析管道"~~ —— 不成立。`ffmpeg exit 4294967256`（= **-40
   ENOSYS**）是**零拷贝路径**在这台机器上跑不起来：`ddagrab` 的 D3D11 纹理直喂 NVENC 时
   `-pix_fmt nv12` 需要 hwdownload，直接 ENOSYS。和码率无关；1920 宽走过滤器路径所以正常，
   一旦切 2560 就会重开零拷贝 → 秒退两次 → 回退。已修（见上表 #6）。
2. ~~"侧车丢帧（253 帧 / 0.66%）是当前病因"~~ —— 本机回环实测 60 秒 0 丢帧，`dropped` 一直是
   253 不动（那是历史累计，含启动和重启期间的）。**它仍然是隐患**（见第四节），但不是这次的复现路径。
3. ~~"侧车帧队列 3→30 的修复退化了"~~ —— 没退化，`dropped` 停在 253、`pending` 0。

## 四、第二轮（同日下午）：把"丢帧 → 参考帧链断"这条也堵了

上一版留的两条 Go 改动已经做完并上线（commit `c1907cce`，侧车版本 **0.5.1**）：

1. **侧车队列满丢帧时置 `needKey`**（`app/rtc-h264/main.go` 的 `session.feed()`）：
   丢帧时我们**不推进 RTP 序号**，接收端根本发现不了少了一帧，后面依赖它的 P 帧全部缺参考帧。
   现在一丢帧就让该会话停推非关键帧、等下一个 IDR（GOP 0.5 秒）—— 画面最多停半秒，不再花屏。
   **只在真丢帧时置位**，绝不用 PLI/FIR 置（之前踩过：PLI 成串 → 长期没帧 → 页面判冻结 → 重连死循环）。
2. **Node 侧丢帧也能通知到侧车**：帧输入头第 5 字节从 `key?1:0` 改成 flags
   （bit0=关键帧、bit1=gap）。`feed264()` 因 `writableLength > 4MB` 丢帧时记 `rtc264PendingGap`，
   下一帧真正写出时带上 gap 位；`/h264-status` 新增 `feedDrops`，`/health` 新增 `gapMarks`。
3. **单测**：`app/rtc-h264/gap_test.go`（3 个用例）。这条路径生产上很难人为触发（要真把 30 帧
   队列塞满），所以用单测把判定逻辑钉死。
4. **工具链**：本机原本没有 Go。这一轮下载了便携版在 `C:\Users\ccj\gotool\go`（1.24.5，
   模块缓存在 `C:\Users\ccj\go\pkg\mod` 还在，编译只要 3.5 秒）：

### 换侧车 exe 的正确姿势（exe 运行时被锁）

不能用 `Copy-Item` 覆盖正在运行的 exe（Access denied / 文件占用）。可行顺序：

```powershell

# 2) 顺手让侧车也退出（它不随父进程死）

# 3) 等 rtc-h264 进程消失后，把新 exe 复制过去（重试几次）
# 4) 等守护进程把服务拉起来，用 curl /health 看 version 是不是新版本
```

### 一条否定结果（别再试）

想用 `RTCEncodedVideoFrame.timestamp` 的跳档来猜丢帧 —— **不成立**。
它的时间戳是侧车**按帧到达时刻**打的，实测相邻帧差值在 1~9576 刻度之间乱跳（90fps 正常约
1000 刻度），根本区分不出"两帧并一帧"。试过一版（1.7 倍阈值 + 1ms 余量）：10 秒里误判 86 次、
白丢 520 帧，每次误判都要等下一个 IDR 才恢复。已在 `wc264-worker.js` 的 `noteInTs` 上方写清原因。

## 六、必读的坑（这一轮新增）

1. **`RTCRtpScriptTransform` / `VideoDecoder` 只在 secure context 可用**。用 `http://100.108.92.22:8660`
   打开页面时 `VideoDecoder` 是 `undefined`（页面会安静地走 `<video>` 老路），
   要复现 WebCodecs 必须用 **`https://dsh-laptop.tailb9b4f0.ts.net/?k=…`**。
2. **screen-server 可能是提权进程**（`Stop-Process` 报 Access is denied）。要重启服务不要硬杀，
   用现成端点：`POST /restart-service?k=<key>`（回复 `{"ok":true}` 后 300ms `process.exit(0)`，
   守护进程约 10 秒后拉起来）；改完 `page.mjs` **必须**重启才生效（ESM 启动时 import 一次）。
3. **`curl -d '{"width":2560}'` 有时不改参数**（body 没进到 handler），但页面里的 `fetch` 一定可以 ——
   排查时优先用页面 console / `dsh_browser_execute` 发请求。
4. 改 `page.mjs` 后跑 `runtime\node.exe app\check-page-js.mjs app\page.mjs`（`node --check` 看不到
   模板字符串里的页面 JS）。本机 `node` 不在 PATH，用 `%LOCALAPPDATA%\PhoneAccess\runtime\node.exe`。
5. 生产目录 `%LOCALAPPDATA%\PhoneAccess` 与仓库 `app\` 必须四个文件一起同步：
   `page.mjs` / `wc264-worker.js` / `screen-server.mjs`。`.bak-sps-20261110-1030` 等是本轮备份。
