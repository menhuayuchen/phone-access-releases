# 传输层改造 · 实施方案（2026-11-05）

## 一、目标

把网页端画面从 **TCP WebSocket** 换到 **UDP 语义**，消除队头阻塞，目标：

- 跨外网（4G/Tailscale 直连或中继）画面延迟 **再降 60–150ms**；
- 丢包 1–3% 时仍能继续播放（丢帧不补、不卡死）；
- 保持现有 1920×1200@60 / H.264 WebCodecs 解码链路不变；
- 失败时必须**自动回落现有 WS**，不影响日常使用。

## 二、候选方案

| 方案 | 原理 | 工期 | 风险 | 浏览器要求 |
|---|---|---|---|---|
| **A. WebTransport(HTTP/3/QUIC)** | 浏览器原生 UDP 流；服务器加 HTTP/3 监听，复用现有 TLS 证书 | 2–3 天 | Node 无内置 HTTP/3，需第三方库；证书/端口与 Tailscale serve 共存要调；Safari 支持较新 | Chrome 97+ / Edge / Safari 18+ |
| **B. WebRTC H.264 视频轨** | 大厂路线：H.264 RTP over UDP，自带抖动缓冲/NACK | 3–5 天 | 现有 `@roamhq/wrtc` 无 H.264 编码器；需换 Go(Pion)/C++ 侧车，工程量大 | 全支持 |
| **C. 自研 UDP + FEC + 中转** | 最可控，但浏览器不能直接收裸 UDP，必须经 WebRTC/WebTransport 中转 | 1 周+ | 最大 | —— |
| **D. 多 WebSocket 并行分片**（兜底优化） | 把帧拆分到多条 TCP 连接，缓解单连接队头阻塞 | 0.5 天 | 治标不治本，提升有限 | 全支持 |
| **E. 强化现有 WebRTC「流畅」模式** | 复用已有 VP8 WebRTC（UDP），只调分辨率/帧率/画质 | 0.5–1 天 | 服务端 VP8 软编，1080p 吃力；画质不如 H.264 | 全支持 |

## 三、推荐路线

**先做 A（WebTransport）**，同时并行 D（多连接兜底）作为过渡：

1. **阶段 1（半天）**：验证 WebTransport 在本机与 Tailscale HTTPS 下的连通性（最小 echo 服务 + 页面 demo）；
2. **阶段 2（1 天）**：把现有「逐帧 H.264」通过 WebTransport 数据流发送，页面 WebCodecs 解码，替代 `/ws-h264`；
3. **阶段 3（半天）**：失败回落 WS、断线重连、码率自适应；
4. **阶段 4（半天）**：真机/跨网测试 + 文档更新。

若阶段 1 判定 WebTransport 不可行（证书/HTTP3 库问题），立即转 **E**（先让「流畅」模式能 1080p 稳定跑，作为低延迟选项），并把 B 作为后续计划。

## 四、验收标准

- 同网：画面延迟 ≤ 现有 WS 版（不劣化）；
- 跨网：延迟比 WS 版低 ≥60ms（用同一段操作录像对比：鼠标点击到画面反应）；
- 1–3% 丢包下不卡死、不黑屏，10 秒内自动恢复；
- 关闭新通道时自动回落 WS；
- 电脑 CPU 增幅 ≤10%。

## 五、风险与回滚

- 所有改动只在独立测试环境（`%TEMP%\pa-*-test`，8662 端口）验证，**不直接动已安装服务**；
- 每阶段结束出验证记录；失败即回滚到当前稳定版（桌面已有 1105 稳定包）；
- 发布仍按老规矩：版本号/打包/上传需用户明确批准。

## 六、需要你决定

1. 选哪条路线（推荐 A，兜底 D/E）；
2. 什么时候开始（建议低峰期/周末整块时间，2–3 天窗口）；
3. 是否允许在测试环境装第三方 npm 包（WebTransport 需要）。
