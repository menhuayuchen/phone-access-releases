# 交接：缓冲持续上涨问题（2026-11-10 深夜）

## 一句话

花屏已彻底修好（侧车丢帧 18.5% → 0%）。剩下一个**未解决**的问题：
**WebRTC 视频缓冲（HUD 的「缓」）会持续上涨**，60fps 下手机端 1 分钟涨到 300ms。
已定位为 **Chrome/WebKit 接收端 jitter buffer 自适应膨胀**，页面侧无法控制。
下一阶段决定：**用 WebCodecs 自研接收端**。

## 二、未解决的问题：缓冲（「缓」）持续上涨

### 实测数据（全部在本机 + 用户手机）

| 配置 | 缓冲涨速 | 丢帧 | 备注 |
|---|---|---|---|
| 2560×1600 @ 240fps | 5.2ms/秒 | 快速涨 | 解码接近极限 |
| 1920×1200 @ 90fps | 5.2ms/秒 | 0 | 解码跑满也没用 |
| **1920×1200 @ 60fps** | **0.94ms/秒**（电脑）/ **5ms/秒**（**用户手机实测 1 分钟 300ms**） | 0 | 手机端压力远大于电脑 |
| 1920×1200 @ 90fps + 限制渲染尺寸 | 0.4ms/秒 | 0 | 画面会缩小（iPhone DPR=3 缩得更小，不可接受） |
| **视频缩到 480px 宽** | **-2.9ms（不涨了）** | 0 | **证明瓶颈是渲染像素面积** |

### 已确认的事实（不要重复验证）

1. **网络完全没问题**：`pktsLost = 0`，`jitter = 0.005`（直连零抖动）
2. **侧车不丢帧**：`dropped = 0`（队列 30 修好后）
3. **解码跑满**：`framesPerSecond = 90`（60fps 配置时 60）
4. **`jitterBufferTarget` 设 0 无效**：实测设成 0 后缓冲照涨（Chrome 无视）
5. **`playoutDelayHint = 0` 无效**（已设，同理）
6. **根因是渲染像素面积**：
   ```
   视频流 1920×1200
   CSS 显示 1707×953 × DPR 1.5 = 渲染 2560×1430 物理像素
   （比视频流本身大 1.7 倍）
   → 渲染管线跟不上 → 每秒少解 4~10 帧 → 积压
   → Chrome 自适应加大 jitter buffer → 「缓」一路涨
   ```
   **iPhone DPR=3**，放大更狠，所以 iPhone 17 Pro 也一样涨。

### 试过但失败的方案

| 方案 | 结果 |
|---|---|
| 改帧协议，Node 传均匀时间戳（13 字节头） | **解码崩溃**（`received 2671 / decoded 460`，75% 丢弃）。**已完全回退**，不要重试 |
| 侧车内部 EMA 平滑时间戳 | 无效（缓冲照涨） |
| 停掉 `getStats` 定时器 | 无效 |
| 强制 `jitterBufferTarget = 0` / `playoutDelayHint = 0` | Chrome 无视 |

## 三、下一阶段要做的事

### 用户已同意：用 WebCodecs 自研接收端

**先试一步**（0 风险，用户还没做）：
- **1280×800 @ 60fps**，看手机端缓冲是否稳定
- 如果稳定 → 问题解决，不用改架构
- 如果还涨 → 才上 WebCodecs

### WebCodecs 接收端方案（如果要做）

**只改浏览器接收端，服务端编码完全不变**（仍是 ffmpeg + NVENC）。

```
服务端（不变）：ddagrab → ffmpeg/NVENC → H.264 → WebRTC 传输
浏览器（新）：
  RTCRtpScriptTransform 截 RTP（绕过 jitter buffer）
  → Worker 里 FU-A 分片重组（丢包就丢整帧，这正是要的）
  → VideoDecoder 解码（WebCodecs）
  → Canvas / OffscreenCanvas 渲染
```

**关键技术点**：
- `receiver.transform = new RTCRtpScriptTransform(worker)` — 拿 RTP
- H.264 FU-A 重组（大帧分多个 RTP 包）
- 丢包检测 → 发 PLI 请求关键帧
- 音画同步（音频仍走 WebRTC 音轨）

**风险评估**：
- **性能**：现有 WebCodecs 路径（`/ws-h264`，走 WebSocket）只能 20-60fps，但那是 Node 转发开销大；走 RTP + Worker 会好很多，**需实测能不能到 90fps**
- **Safari 兼容**：`RTCRtpScriptTransform` iOS 15.4+ 支持但实现有差异，**iPhone 可能需要降级方案**
- **工作量**：估计 2-3 天开发 + 大量真机测试

### 参考：大厂怎么做

- **Native 客户端**（Parsec/Moonlight/AnyDesk）：自己写 UDP 协议，**零缓冲**，宁可丢帧不延迟
- **云游戏**（Stadia/GeForce Now）：WebRTC 传输 + **WebCodecs 自研接收端**（`RTCRtpScriptTransform`）
- **Chrome Remote Desktop**（最像我们）：浏览器 + WebRTC，**同样有这个问题**，Google 也没彻底解决，只能限制分辨率 + 定期重建

## 四、必读的坑（这一轮踩过的）

1. **改 `app/page.mjs` 必须重启 `screen-server`**
   `page.mjs` 是 ESM 模块，`screen-server.mjs` 启动时 `import` 一次。改完不重启 → 页面一直是旧的（清了 Service Worker 缓存也没用）。

2. **帧协议改动必须 Node 和侧车同时更新**
   只改一边 → 解码崩溃。**13 字节头那次就是这样崩的，已完全回退**。

3. **`#stat` 的显示由 `MutationObserver` 控制**
   `page.mjs` 里有个 `MutationObserver` 监听 `#hud`，每次变化调用 `applyVis()`，里面会把 `#stat` 设成 `display: ''`。所以**直接设 `stat.style.display` 会被覆盖**，必须在 `applyVis()` 里改。

4. **改 `.ps1` 必须 UTF-8 with BOM，且不能有 `//` 注释**
   PowerShell 会把 `//` 当命令执行。

5. **编辑后 `main.go`/`.ps1` 的 BOM 会被 `edit` 工具剥掉**，要重新加。

6. **侧车编译命令**（Go 1.24 需要联网下载，用国内代理）：
   ```powershell
   $env:GOPROXY = 'https://goproxy.cn,direct'
   $env:GOTOOLCHAIN = 'auto'
   & 'D:\download\办共\phone-access-product\tools\go\bin\go.exe' build -o out.exe .
   ```
   - 不要设 `GOSUMDB=off`（会让 toolchain 校验失败）
   - `go.mod` 要求 1.24，本地工具链是 1.23.4 → 靠 `GOTOOLCHAIN=auto` 自动下载

7. **检查 exe 里的中文字符串要用 UTF-8 解码**
   `[Text.Encoding]::ASCII.GetString()` 会把中文变乱码，导致误判"没有这个字符串"。

8. **检测"改了没有"要认准具体位置**
   用 `#stat { display: none` 做正则检查会误匹配别处的 `#stat { display: none !important; }`。
