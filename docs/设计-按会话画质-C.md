# 设计：按会话画质（C）—— 让两台设备各自决定画质

> 状态：**设计定稿，未实现**（2026-11-10 深夜）。前置的 A+B 已上线：
> A = `/h264-quality` 幂等（参数没变不重启编码器）；B = WebRTC 回落标记 10 分钟 TTL + 手动重连清标记。
> A+B 已经把"两台设备设置不同 → 黑屏且不恢复"这个现象消掉了；C 是让**每台设备真的各自跑自己的档位**。

## 1. 为什么现在做不到

现状是**单例**：

```
ffmpeg(1 路, 全局 H264_W/FPS/KBPS) --fMP4/pipe--> Node 解析 --TCP 9900--> rtc-h264.exe(1 个)
                                                        └--TCP 9902-- 音频
```

- `screen-server.mjs` 里 h264 是模块级单例：`h264.proc / h264.pending / h264.initInfo / h264.tsUs / h264.clients`。
- 侧车 **一条帧输入**（`-tcp`），所有 WebRTC 会话共用这一个码流。
- 所以"每台设备不同画质"在物理上不可能，除非有**多路码流**。

## 2. 侧车已经具备的能力（决定了实现路径）

`rtc-h264.exe` 的 flag（`main.go:874-886`）：

```
-port       HTTP/信令端口（默认 9800）        -host   监听地址（默认 127.0.0.1）
-tcp        帧输入 addr:port                   -audio  音频输入 addr:port
-turn-port  内置 TURN UDP（0=关）              -log    日志文件
-fps/-loop  仅测试用
```

→ **同一个 exe 可以起第 2 个实例**（不同 port/tcp/audio，`-turn-port 0` 不抢 TURN）。
这就是最省事、且**完全不碰现有主链路**的做法。

## 3. 方案：按需第二路（primary 不动，纯增量）

### 3.1 进程与端口

| | 主路（现状） | 第二路（新增） |
|---|---|---|
| 侧车 HTTP | 9800（配置 `rtc264.port`） | 9810 |
| 帧输入 | 9900 / 音频 9902 | 9910 / 9912 |
| TURN | 3478（主路独占） | `-turn-port 0` |
| ffmpeg | 现有 `h264Start()` | 新增 `h264Start2()`，只支持全屏 ddagrab + NVENC（不做窗口模式/零拷贝） |
| 解析 | 现有 `processH264Buffer`（单例 h264） | 新增 `parse2()`，用**独立状态对象** `st2`，代码可复制自现有解析器 |
| 会话绑定 | `/rtc264/offer`（→ 9800） | `/rtc264/offer?stream=2`（→ 9810 的 `/offer`） |

### 3.2 会话与档位

- 页面每次建会话前先 `POST /h264-quality {width,fps,kbps,stream?:2}`：
  - 服务端记录 `sessions[streamId] = { profile, lastSeen }`；
  - 若当前只有主路会话且新档位与主路不同 → 分配 `stream=2` 并在回复里返回 `stream:2`；
  - 若第二路不可用（起不来/GPU 拒绝）→ 回复 `stream:1`（共享主路，回到今天的语义）。
- 页面把 `stream` 带进 `/rtc264/offer?stream=2`，服务端代理到对应侧车。
- 会话结束（`/health` 里 sessions=0 或 ICE closed）→ 5 分钟后回收第二路（kill ffmpeg + 侧车）。

### 3.3 上限与保护

- **最多 2 路**（写死）。第 3 台设备一律共享主路（按最高档）。
- 第二路的 `fps×像素` 同样走现有 `PIXEL_BUDGET` 与 `DEVICE.caps` 封顶。
- 第二路起不来时**必须**回落到主路，并且页面提示"当前与他人共享画质"——不能黑屏。
- 两路都写 `h264-quality.state.json` 会把状态搞混：**只让主路落盘**，第二路是临时态。

## 4. 风险清单（实现时必须逐条验）

1. **两个 ddagrab 同时抓同一块屏**：Windows 允许多个 Desktop Duplication 客户端，但要在本机实测
   （分别 2560/120 与 1920/60）。抓不到就退化为：第二路只做 **scale**（同一份采集不可能，需第一步成功）。
2. **NVENC 并发会话数**：消费卡旧驱动可能只有 2~3 路。要用 `nvidia-smi` 或实测确认；起不来就走回落。
3. **CPU/带宽翻倍**：两路 2560 会让 CPU 飙；必须在 `DEVICE.level=good` 且当前主路不是 240fps 时才允许第二路。
4. **音频**：现在音频走主路 9902。第二路若也要声音，要么复用主路的 Opus（两路 Pion 各自编码），
   要么第二路也开 `-audio 9912` 并让 Node 再连一条。**建议先不做第二路音频**（复用主路 feed 即可，声音一样）。
5. **页面协议**：`stream` 参数必须缺省安全（没带=1），老页面完全不受影响。
6. **端口冲突**：9810/9910/9912 要在 `rtc264` 配置里可覆盖，且启动时探测占用。

## 5. 验收用例（必须全过才发布）

1. 单设备：设置 2560/120 → 行为与今天**完全一致**（不看日志都感觉不到改了）。
2. 两台设备相同设置：只有一路；第二台加入不重启、不掉帧。
3. 两台设备不同设置：两路各自生效；两边都能看到自己档位的画质；任一台关掉后另一台不受影响。
4. 第二路起不来（人为把 9810 占用）：两台设备**都有画面**（共享主路），页面有提示，无黑屏。
5. 弱机（`DEVICE.level>=1`）：不尝试第二路，直接共享。
6. 音频：两路同时有声时不能出现双份/回声。
7. 手机侧：两台设备都点「重新连接」×3 次，都能恢复（B 的 TTL 生效）。

## 6. 工作量

| 部分 | 估计 |
|---|---|
| 第二路 ffmpeg + 解析 + 回收（server） | 4~6 小时 |
| 第二路侧车拉起 + offer 代理 | 1~2 小时 |
| 页面协议 + 提示文案 | 1~2 小时 |
