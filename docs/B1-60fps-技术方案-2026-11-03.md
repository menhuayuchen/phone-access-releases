# B1 · 60fps / H.264 硬编 · 技术方案与首轮测量（2026-11-03）

> 用户 2026-11-03 建议：参考开源的 **Sunshine（被控端）+ Moonlight（客户端）**，
> 我们的目标是「在它们的基础上更容易配置」。
> 这份文档先做**测量**（B1 第一步），再给路线对比和里程碑。**本轮没有改产品代码**；
> 只有 `app/pipe-bench.mjs` 修了一个解析 bug（见第七节）。

---

## 一、现状测量（本机 2026-11-03 18:5x）

环境：Ryzen 9 8945HX / 2560×1600@240Hz / Windows 11；`capture.exe`（GDI `CopyFromScreen` + JPEG 编码），
用独立的 capture 实例 + 修好的 `pipe-bench` 测 20 秒，取最后一段：

| 配置（宽/帧间隔/JPEG 质量） | 实测帧率 | 数据量 | capture 单进程 CPU |
|---|---|---|---|
| 1280 / 33ms / q70 | 20.7 fps | 1.9 MiB/s | ≈1.0 核 |
| 1920 / 33ms / q70 | 16.0 fps | 2.8 MiB/s | ≈1.0 核 |
| **2560 / 33ms / q70（生产档）** | **29.8 fps** | **8.4 MiB/s** | ≈0.9 核 |
| 2560 / 16ms / q70（60fps 目标） | 34.1 fps | 9.7 MiB/s | ≈1.0 核 |
| 2560 / 16ms / q50 | 34.7 fps | 7.7 MiB/s | ≈1.0 核 |
| 1440 / 16ms / q70 | 19.5 fps | 2.2 MiB/s | ≈1.0 核 |

结论（三条，都很关键）：

1. **2560 档已经吃满 33ms 的 30fps 上限**；把间隔改成 16ms 只提到 ~34fps —— **采集+JPEG 编码是瓶颈**，
   单核 ~100%，不是网络。
2. **带宽**：2560/q70 是 8.4–9.7 MiB/s ≈ **70–78 Mbps**；如果真要 60fps，MJPEG 需要 ~20 MiB/s（160 Mbps）——
   手机流量、Tailscale 中继都不可能。**60fps 不能用 MJPEG 实现**。
3. **降档不提速**：1280/1440 反而更慢（20.7 / 19.5 fps）。原因是抓屏永远是原生 2560，发送宽度更小时
   要额外做 GDI+ 缩放——和 2026-10-30 的记忆一致（"降档不提速"）。所以优化不能只靠降宽度。

> 测量方法：把 `capture.exe` 以独立实例（独立管道、viewers=1）启动，用修好的 `pipe-bench` 连管道读 20 秒。
> 每条只跑一次（±10% 噪声），但"30fps 上限 / 单核吃满 / 60fps 时带宽翻倍"这几个结论是稳的。

## 二、Sunshine / Moonlight 参考（它们怎么做到的）

- **Sunshine** 是 Moonlight 的开源被控端：Windows 上屏幕采集用 **DXGI Desktop Duplication**
  （配置项 `capture = ddx`）或 Windows.Graphics.Capture（`wgc`，beta），编码用 GPU 硬件编码器
  `nvenc` / `quicksync` / `amdvce`（或 `software`），码率/帧率由客户端请求 + `max_bitrate`、`minimum_fps_target`、
  `fec_percentage`（前向纠错）、`qp` 等参数控制；网络端口从 `47989` 起（UDP 视频流）。
- **Moonlight** 是原生客户端（Windows/Android/iOS/…），走 NVIDIA GameStream 协议（私有 RTSP + UDP 视频），
  所以能稳定 60fps：**硬编 + UDP + 丢包重传/FEC + 原生解码**。
- 参考链接：[Sunshine 配置文档](https://docs.lizardbyte.dev/projects/sunshine/latest/md_docs_2configuration.html)、
  [Sunshine 仓库](https://github.com/LizardByte/Sunshine)、[Moonlight 官网](https://moonlight-stream.org/)。

**我们能借什么、不能借什么：**

| | 借 | 不借 |
|---|---|---|
| 采集 | DXGI Desktop Duplication（直接拿 GPU 纹理，不用 GDI 读回） | 它的 X11/KMS/VAAPI 等 Linux 路径 |
| 编码 | 硬件编码（NVENC/AMF/QSV，Media Foundation 或厂商 SDK） | 它的 `software` 默认参数（我们是办公/轻量场景） |
| 协议 | 低延迟码控、FEC 思路 | **私有 UDP 协议**（手机端是浏览器，没有 Moonlight 客户端） |
| 配置 | "尽量自动"的思路 | 它的手动配置向导（编码器/端口/码率都让用户选——这正是我们要避免的） |

**我们的差异化不能丢**：手机免装 App（浏览器/PWA）、Tailscale 直连、零配置。
所以 B1 的目标不是"复刻 Moonlight"，而是"在浏览器里做到 60fps 的办公级流畅"。

## 三、路线对比

| 路线 | 做法 | 预期 | 风险/工作量 |
|---|---|---|---|
| **A. 先榨干 MJPEG** | 跳过不必要的缩放（发送宽度=抓屏宽度时不缩放）、换 turbojpeg/WIC 编码、水平分块并行编码、q 自适应 | 2560@30fps 稳住、CPU 降到 ~0.5 核；**到不了 60fps** | 低，1 天 |
| **B. WebRTC 提档** | 现"流畅模式"是 WebRTC（libwebrtc，1280 宽）。把它提到 1920/2560、请求 60fps，用浏览器原生解码 | 1920@60fps 有机会；中继时码率要压 | 中，2–3 天（SDP/码率/兼容性） |
| **C. 自建 H.264 硬编 + WebCodecs** | 新采集：DXGI Duplication → GPU 纹理；新编码：Media Foundation H.264 硬编（AMD AMF / NVENC / Intel QSV 回落软编）；输出 Annex-B/fMP4 经 WebSocket；手机用 **WebCodecs `VideoDecoder`** 解码 → canvas | 1440p/1920p@60fps、带宽 5–15 Mbps、CPU 大幅下降 | 大，1–2 周；手机兼容性（Safari 16.4+/Chrome 94+，可回落 MJPEG） |

> WebCodecs 兼容性参考：[MDN WebCodecs API](https://developer.mozilla.org/zh-CN/docs/Web/API/WebCodecs_API)。

**建议顺序**：A（保底，马上可选）→ B（低成本试 60fps，验证手机端能不能吃）→ C（要"游戏级"才投）。
理由：C 的收益最大但工程量也最大；先用 B 验证"手机浏览器 60fps 解码 + 显示"这条链路，
再决定要不要写 C 的采集/编码端。如果用户只要求"看起来不卡"，A+B 可能就够。

## 四、验收指标（做 B1 时按这个验）

- 帧率：1920×1080 / 2560×1600 下 55–60fps（`/health` 的 in/out fps）；
- 端到端延迟：手机点一下到画面响应 < 120ms（本地 tailnet 直连；中继另算）；
- 带宽：1920@60fps ≤ 8 Mbps、2560@60fps ≤ 15 Mbps（可调码率）；
- CPU：capture/编码进程 ≤ 0.5 核（2560@60fps）；
- 兼容性：Chrome/Edge Android、Safari 16.4+；不支持 WebCodecs 时**自动回落 MJPEG**（不能变砖）；
- 稳定性：连续 30 分钟无堆积、无内存泄漏；手机锁屏再回来能恢复。

## 六、风险

- **硬件差异**：AMD/Intel/NVIDIA 编码器 API 不同，必须做"找不到硬编就回落"；不能要求用户装驱动/配参数。
- **手机解码能力**：中低端手机 2560@60 解码可能掉帧；需要按设备能力选分辨率/码率（类似 Moonlight 的自适应）。
- **Tailscale 中继**：走 DERP 时带宽/延迟都差，60fps 意义有限；要检测直连/中继（A3 面板已有数据）并自动降档。
- **MJPEG 兼容层必须保留**：WebCodecs 不可用、或用户选"省流量"时继续用现有链路。

## 七、附：测量工具与这次修掉的 bug

`app/pipe-bench.mjs` 读管道时有个解析 bug：读完 4 字节长度后如果一帧数据还没到齐，
它 `return` 等下一批数据，但**下一批数据进来时会重新读"长度"**（把帧内容当成长度）→ `desync`。
修法：读长度前判断 `frameLen === 0`（已在本轮一并修复）。
用法：`node pipe-bench.mjs <管道名>`（默认 `dsh-screen-frames`），跑 20 秒自动出 fps/带宽。

同机实测还发现：**GDI+ 缩放是隐形成本**——发送宽度小于抓屏宽度时反而更慢（1280 比 2560 慢 ~30%）。
所以路线 A 的第一条就是"不需要缩放时绝不缩放"。
