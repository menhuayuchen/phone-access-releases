# B 方案：Go + Pion 的 H.264 低延迟传输（实施计划 2026-11-05）

## 目标

用大厂同款路线取代 TCP WebSocket 传视频帧：

- 现有 ffmpeg（NVENC）→ 逐帧 H.264 保持不变；
- 新增 Go 侧车：把逐帧 H.264 打成 **RTP**，通过 **WebRTC 视频轨**推给浏览器；
- 浏览器用原生 `<video>` 播放（硬件解码、自带抖动缓冲/丢包恢复/带宽自适应）；
- 失败或协商不成功时自动回落现有 WS（`/ws-h264`），不影响使用。

## 架构

```
ffmpeg(NVENC) -> fMP4 解析 -> 逐帧 H.264 (已有 Node 逻辑)
                               |
                     stdin/本地 socket  →  Go 侧车 (Pion WebRTC)
                                             |  RTP / SRTP over UDP
                                     手机浏览器 <video>
```

- Node 端把"逐帧 H.264 + key 标记"通过本地 TCP 或 stdin 发给 Go 侧车；
- Go 侧车用 Pion 的 `TrackLocalStaticSample`（H264 payloader）推送；
- 浏览器 `<video>` 直接播，无需 WebCodecs；
- 信令沿用现有 HTTPS 页面：Node 提供 `/rtc-offer`（把 offer/answer 在 Node 与 Go 间转发），或 Go 自己开一个 127.0.0.1 的 WS 由页面直连。

## 里程碑

1. **M1 环境**（0.5 天）：装 Go 工具链；`go mod` 拉 Pion；跑通官方 `play-from-disk` 示例在浏览器播放。
2. **M2 最小推流**（0.5 天）：Go 侧车接受简单帧协议（len+key+data），Pion 建 track，浏览器 `<video>` 收到画面。
3. **M3 接入真实编码**（0.5 天）：Node 把 ffmpeg 帧转给 Go；验证 1920×1200@60、关键帧对齐。
4. **M4 联调与回落**（0.5–1 天）：信令、鉴权、tailnet 直连/中继、失败回落 WS、HUD 显示 transport。
5. **M5 真机验收**：同网/外网各测一轮，记录延迟、帧率、丢包容忍。

## 验收标准

- 同网：延迟不劣于现有 WS；
- 外网：比 WS 低 ≥60ms 且丢包 1–3% 不卡死；
- 失败自动回落 WS，页面无黑屏；
- 电脑 CPU 增量 ≤10%。

## 风险

- Pion 的 H.264 payloader 对 SPS/PPS 与关键帧要求严格，需要编码端保证 IDR + SPS/PPS 随关键帧发送；
- WebRTC 在 Tailscale 上需 ICE 直连（tailnet IP），必要时用 host candidate；
- 侧车进程管理（启动/退出/端口）要纳入产品安装与自启。
