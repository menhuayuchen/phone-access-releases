# B 方案：Go + Pion 的 H.264 低延迟传输（实施计划 2026-11-05）

> 2026-11-05 傍晚更新：M1–M4 完成，稳定性改造落地并本机验证通过；
> **M5 真机（手机 4G + Tailscale）验收待用户配合**，发布仍需明确批准。

## 目标

用大厂同款路线取代 TCP WebSocket 传视频帧：

- 现有 ffmpeg（NVENC / h264_mf）→ 逐帧 H.264 保持不变；
- 新增 Go 侧车：把逐帧 H.264 打成 **RTP**，通过 **WebRTC 视频轨**推给浏览器；
- 浏览器用原生 `<video>` 播放（硬件解码、自带抖动缓冲/丢包恢复/带宽自适应）；
- 失败或协商不成功时自动回落现有 WS（`/ws-h264`），不影响使用。

## 架构（当前实现）

```
ffmpeg(NVENC/h264_mf) → fMP4 解析 → 逐帧 H.264 (Annex-B, 已有逻辑)
        ├─ /ws-h264 WebSocket ────────────────→ 页面 WebCodecs（原有主链路）
        └─ TCP 127.0.0.1:9900 (u32 len + u8 key)
                 └→ rtc-h264.exe（Pion WebRTC）
                      ├─ RTP/SRTP over UDP；host 候选 = tailnet IP（SetNAT1To1）
                      └─ 内置 TURN（udp 3478，绑 tailnet IP + 回环，凭据每次启动随机）
                               └→ 手机 <video> 原生解码
```

- 信令：页面 → `/rtc264/{offer,answer,close}`（同源，Node 代理到侧车 `127.0.0.1:9801`）；
  侧车 `/offer` 返回 `{ sid, sdp, turnOk, turnPort, turnUser, turnPass, turnHost }`。
- 页面开关：`?rtc264=1`；`?rtc264=relay` 强制 TURN 中继（排查用）。
- 失败回落：ICE failed 或 12 秒没画面 → 重试 2 次 → 回落 `/ws-h264`，不黑屏。

## 本轮稳定性改造（2026-11-05 傍晚）

1. **每条 /offer 新建一条 PeerConnection**。旧版进程启动时建一条、SDP 缓存复用，
   页面刷新/手机切网后再来永远协商不上（这是"不稳定"的头号原因）。
2. **帧泵按会话排队 + 关键帧门控**：新会话等到 IDR 再开始推，不会从半路解码花屏；
   慢会话不会拖住别的会话。
3. **会话回收**：disconnected 15 秒不回来自动 drop；新会话接入时清掉 10 秒没输出的僵死会话；
   janitor 每 30 秒兜底清理 failed/过期 offer。
4. **内置 TURN 中继**：手机在运营商 NAT / 对称 NAT 后面时，靠 relay 候选也能连；
   凭据每次启动随机生成、经 `/offer` 下发，不再写死在页面里；监听只有 tailnet 地址+回环。
5. **播放端**：`playoutDelayHint` / `jitterBufferTarget` 40ms；HUD 显示「直连 / 中继 · 分辨率 · 帧数」。
6. **Node 侧**：
   - 侧车幂等拉起；启动前先 `/shutdown` 收掉上一代残留（supervisor 重启 node 时子进程不退，
     旧版会留下"旧版本 + 旧凭据"的侧车占着端口）；
   - 帧输入背压：写缓冲 >4 MB 直接丢帧，不让 Node 内存涨；
   - 轮询侧车 `/health`：有会话 → 保证 ffmpeg 在跑；无会话无 WS 观众 15 秒 → 停编码器；
     有会话但 5 秒没帧 → 重启编码器（20 秒限频）；
   - 侧车 HTTP 只监听 `127.0.0.1`（旧版是 `0.0.0.0`），日志写 `rtc-h264\sidecar.log`（1 MB 轮转）。
7. **GOP 从 1 秒降到 0.5 秒**（`-g fps/2`）：丢包或新会话时恢复更快。

## 本地验证记录（2026-11-05 傍晚，headless Chrome 156）

| 场景 | 结果 |
|---|---|
| 产品页 `?rtc264=1`（直连，候选对 prflx>host） | 1920x1200，首帧 1.1s；90 秒浸泡 45 次采样 0 异常，解码 5119 帧 / 138 MB |
| 产品页 `?rtc264=relay`（强制中继，relay>host） | 1920x1200，首帧 2.7–3.1s → 证明 TURN 中继链路可用 |
| 页面刷新（reload） | 旧版必定失败；新版 0.8–2.4s 恢复画面（每次新建会话） |
| 侧车不可用（把 exe 移走） | 自动回落 `/ws-h264`，1.6s 出画面，URL 里的 `rtc264` 参数被移除 |
| 无人观看 15–20 秒 | 侧车 sessions→0，ffmpeg 自动退出（CPU 归零） |
| Node 被 supervisor 重启 | 新 Node 通过 `/shutdown` 收掉旧侧车再拉起，端口 9801 不再被占 |

## 风险与已知限制

- Pion 的 H.264 payloader 要求 Annex-B + 关键帧带 SPS/PPS（AVCC 直接喂会 no video）；
- 真机锁屏后 Chrome 可能把页面冻结，回到前台时靠 `visibilitychange` 重连（本地只验证了 reload）；
- 侧车没有做 PLI 反向请求，浏览器中途丢包要等下一个 IDR（0.5 秒内）；
- TURN 是"自己给自己做中继"（PC 内），手机→TURN 的 UDP 仍要过 Tailscale；防火墙靠
  Tailscale 自带的 `Tailscale-In` 放行，未额外加规则（需要真机确认）。
