## 二、质量阶梯压测（qos-test.mjs，120fps 档 4 分钟；手机真机）

**稳态很好，但被一段"客户端自己停摆"污染，按工具阈值判不达标。**

| 指标 | 数值 | 说明 |
|---|---|---|
| 解码 / 画出 | 108.5 / 106.8 fps（屏 119.6Hz） | 8 条诊断的平均，含下面那段掉帧 |
| 缓冲 | 中位 6ms / **p90 89ms** | p90 由 18:24:00~18:24:40 那段 89ms 拉高 |
| 到达节奏 | p90 18.2ms / max 61ms（理想 8.3） | 解码成簇到达 |
| 呈现停摆 | **10 次**（1180ms 间隔成串） | 触发页面"雪崩看门狗"→ 重建接收端 |
| 音频 | 丢 0 B / 写超时 0 / 延迟 0~10ms | 完全正常 |
| 音画偏差 | 中位 14ms / p90 87ms | p90 同样来自那段 |
| 侧车丢帧 | 0 | |
| 判定 | ❌ 画出/屏幕 89%<90%、缓冲 p90 89>80ms、停摆 10 次 | |

**8 条诊断里有 5 条是稳态**：解 106~122 / 画 106~120（**98~100%**），缓冲 2~10ms，`per` 8.2~8.8ms。
坏的 3 条都集中在 18:24:00~18:24:40：日志里 `停摆间隔=1157|1158|1159…` 成串 → `[rtc264-stop] 原因=retry:avalanche`
→ 编码器重启 2 次 → 页面自动降档到 90fps（`auto=true`）。手机端 rAF 从 120 掉到 115/118、`vid` 从 61 掉到 29，
符合"手机屏幕变暗/被系统降频或切后台"的特征（测这段时手机不在我手里）。

**结论：稳态指标达标（画出 98~100%、缓冲 2~10ms、音频 0 丢），但"客户端停摆 → 看门狗重建 → 降档"这条链
会被误触发一次就毁掉整个样本。下一轮压测要固定在手机前台常亮，并把"停摆次数"和"雪崩重建"分开计数。**

## 三、崩溃恢复（recovery-test.mjs，杀编码器 3 轮）

| 轮次 | 杀掉编码器 | 进程重新拉起 | 重新开始产帧 | 判定 |

## 五、结论

- 稳定性：5 个场景 0 卡顿、0 音频异常、内存无泄漏趋势。
- 呈现：本机 Chrome（240Hz）画出 76.9→**120.0**（与解码 121 齐平）；手机（120Hz）画出 95→**118.3**。
- 关键帧：体积降 63~65%，PLI 降 93%，"突发把链路挤坏"这条链被切断。
- 恢复：编码器崩溃 1.1~3.8 秒恢复出图。
- 剩余风险：`feedCad max` 仍有 30~99ms 的偶发尖峰（编码/进程调度抖动），极端情况下会看到单帧顿一下；
  120fps 内容 + 120Hz 屏时，到达成簇会让队列偶尔撞上 8 帧安全上限（本轮约 8 帧/秒被丢），
  后续可考虑"按到达节奏自适应加深缓冲"或"显示端直接按最新帧丢弃"再做一版。
