## 二、规则（必须遵守）

1. **发版规则**：每出一个大版本，必须**自用版 + 发布版两套**都打；**任何发布都必须先得到用户明确同意**（改 version、传 Gitee/GitHub、打 tag、改站点下载都算发布）。
2. **`.ps1` 必须 UTF-8 with BOM**；编辑后必须 `[Parser]::ParseFile` 检查 + 实际跑一次。
3. **永远不要往 .ps1 里写 JS 风格的 `//` 注释**——PowerShell 会把它当命令，运行时报 CommandNotFound，而且**语法检查发现不了**（本会话踩了两次）。
4. 改 `page.mjs` 里内联脚本后，必须：从**线上页面**抽出 `<script>` → `node --check`；再到浏览器确认 `window.__paExp` 存在（脚本完整跑完的判据）。本会话出过 `IS_DESKTOP` TDZ，症状是"一直转圈：正在连接画面"。
5. **不要用 PowerShell 控制台判断中文文案**（会显示成乱码，造成误判）；用 `node` 读文件 + `split` 计数，或 `Select-String -Encoding UTF8` 对文件查。
6. 重启服务用 `POST /restart-service`（只退出进程）。**不要用 `/offline/on` 重启**——它会把 `screen.offline` 写成 true，用户多次发现"离线模式自己开了"。
7. **Sunshine 配置不要只靠 API POST**（不会持久化，会被重写成只剩几行）。改 `C:\Program Files\Sunshine\config\sunshine.conf` 要提权，改前备份，改完重启 `SunshineService`；重启脚本要 try/finally 保证服务最终是 Running（本会话出过一次服务停着没起来 + conf 被写空）。
8. 用户明确说过：**画质与流量正文不要改**；文案要"说人话"，但技术细节放进折叠区。
9. 任何涉及"地址/状态显示"的改动，**先用接口实测返回值**，再确认页面渲染，不要只看代码。
10. 不要留半成品开关在生产配置里：`screen.lan` 目前默认 false，请求级仍被安全过滤拦（见待办）。

## 八、事故复盘（2026-11-07 18:2x）：手机一直"正在连接画面…"

**现象**：页面 UI 正常加载，但画面永远转圈（`帧0/解0`）。

**直接原因**：`capture.exe` 从 18:21 起**不再出帧** —— 进程还在、CPU 不涨、管道 `\\.\pipe\dsh-screen-frames`
连上但 0 字节；`pipe-diag.log` 里写着 `IOException: 所有的管道范例都在使用中`。
同时 ffmpeg(ddagrab) 拿不到帧，反复 `exit 4294967256`（-40）→ 就是那段崩溃重启循环。

**触发条件**：18:19–18:21 我把 screen-server 重启了多次，旧进程留下的**半开管道连接**占住了
capture.exe 的**单实例管道**（`maxInstances=1`），capture 再也建不出新管道、也就发不出帧。
（教训：不要在几分钟内反复重启 screen-server；真要重启就按下面"正确顺序"来。）

**为什么没有自愈**：`supervise.ps1` 有"10 秒没帧就杀 capture 重启"的看门狗，但它**只在 `viewers>0` 时才判**；
而 `screen-server.mjs` 的 `wanted()` 只统计 MJPEG 流和流畅模式，**漏了清晰模式的两种观众**
（MSE/H.264 的 `h264.clients` 和 Pion 侧车的 `rtc264Status.sessions`）→ viewers 恒为 0 → 看门狗形同虚设。

**修复**：`wanted()` 把 `h264.clients.size + rtc264Status.sessions` 也算进去。
现在只要有人在看清晰模式，`viewers.count` 就 > 0，看门狗就能在 capture 卡死时自救。

**正确重启顺序（卡住时照做）**：
1. `Stop-Process capture`（先停抓屏）
2. 让 screen-server 退出（`POST /restart-service`）
3. 用 `start-screen.ps1 -Quiet` 拉起（会先起 capture 再起服务）

验证：`GET /health` 里 `viewers=1 age=0.x source=pipe`，页面 `videoWidth>0`。

### 补充（同日 19:2x）：`/health` 的 `rtc.peers` 不是幽灵连接

排查时容易误读：清晰模式下 `/health` 里 `rtc.peers=1`、`frameAge` 一直很大，
看着像"切模式后连接没释放"。**其实不是**——那是清晰模式的**纯音频连接**（`/rtc?audio=1`），
它本来就不传视频。日志里能看到正常关闭：`rtc: viewer closed ... code=1005 pc=closed`。

真正修掉的是**重复计数**：同一位观众（视频走 Pion 侧车 + 音频走 rtc）会被算成两个，
`/health` 显示 `viewers=2`。现在 `rtc.stats()` 多了 `audioOnly` 字段，`wanted()` 里用
`rpVideo = peers − audioOnly`，不再重复。实测同一位观众：`viewers=1`、`peers=1 audioOnly=1`。

### 补充（同日 20:0x）：定时开关机「加入」永远失败

**现象**：面板里点「加入」总是提示"休眠/关机时间要写成 HH:mm"，自定义规则加不进去；
快捷预设却能加（它不走校验）。后端一直是好的（`power-last.json` 显示任务 Ready、`wake:true`）。

**根因**：`page.mjs` 里两处时间校验的正则被写坏了——
`/^([01]?d|2[0-3]):[0-5]d$/`（`\d` 变成了字面 `d`），于是 `23:00` 永远不匹配。
同一份校验在服务端 `screen-server.mjs` 是对的（`\d`），所以只有页面侧失败。

**修法**：两处改回 `\d`。实测「加入」22:30/06:45 工作日后：规则文件 2 条、系统里 4 个计划任务全 Ready；
删掉后回到 1 条 / 2 个任务。边界：`23:00`/`07:05`/`7:05` 通过，`24:00`/`23:0`/空/abc 拒绝。

**教训**：这类"转义被吃掉"的正则问题，**服务端和客户端要各测一次**——只测接口会漏掉页面校验。

### 补充（同日 20:0x）：定时休眠成功，但**定时唤醒没兑现**

**实测复现**：规则「仅一次 20:05 休眠 / 20:07 唤醒」→ 20:05 确实休眠（Kernel-Power 42），
但 **20:06:04 就被"某物"提前唤醒**（Kernel-Power 107），到 20:07 该醒时机器仍睡着，
最后是用户 20:09 按键唤回（`powercfg /lastwake` 显示"唤醒源计数 0"，即不是定时器唤醒）。

**排查结论**（不是配置错）：
- 唤醒任务 `WakeToRun=True`、`StartWhenAvailable=True`；`RTCWAKE` 交流/直流都是"启用"（1）；无组策略覆盖；
- `powercfg /waketimers`（提权）**确实看到**系统为 07:30 注册了唤醒定时器（`SystemEventsBroker` 设置，说明"将执行 NT TASK\轻屏-电源-…-唤醒"）；
- `powercfg /devicequery wake_armed` 显示 **网卡（有线/无线）、键盘、鼠标都开着"允许唤醒"** ——
  这些就是那次 62 秒后被提前叫醒的来源，而定时器一旦被这种"意外唤醒"消耗，到点就不会再醒。
- 另外：任务计划器的 Operational 日志默认是**关闭**的，所以看不到任务的触发/唤醒细节（排查时先 `wevtutil sl Microsoft-Windows-TaskScheduler/Operational /e:true`）。

**修法（已完成并验证）**：`power-apply.ps1` 的 `New-WakeTrigger` 改为**每个唤醒任务给 3 个触发点**
（目标时间、+3、+6 分钟）。第一个被意外唤醒消耗掉后，睡回去时下一个触发点会重新注册唤醒定时器。
实测任务已知有 07:30 / 07:33 / 07:36 三个 Daily 触发、`WakeToRun=True`。

**后续可做（未做）**：
1. 可选"睡眠期间关掉鼠标/键盘/网卡的唤醒权限"（`powercfg /devicedisarmwake` 思路，见 `powercfg /devicedisablewake`），能减少误唤醒；
2. 把"应用后校验 waketimers"做进引擎（需要提权）。
