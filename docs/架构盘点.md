## 0. 一分钟读懂

一套进程：1 个 DSH 网页实例 + 3 个反向代理 + 画面 2 个（screen-server / capture）+ 声音 1 个（audio）+ 注入 1 个（input）+ 守护 1 个（supervise），全部跑在同一台 Windows 桌面机上，对外只经 Tailscale：

```
 手机浏览器（page.mjs）
   ① 看画面     ── 8660 ─────────────▶ screen-server.mjs ──管道──▶ capture.exe
   ② 点触控     ── 8660 POST /input ─▶ screen-server.mjs ──管道──▶ input.exe ──▶ SendInput
   ③ AI 对话    ── 8642 ─────────────▶ tunnel-proxy ──▶ 127.0.0.1:8642（DSH --profile web）
   ④ 听声音     ── 8660 /ws-audio 或 WebRTC 音频轨 ──▶ screen-server ◀──管道── audio.exe（WASAPI loopback）

   所有服务只 bind 在 Tailscale IP 或 127.0.0.1；手机必须登录同一 tailnet 才能到达。
   tailnet 名字入口：tailscaled ──serve :80──▶ 127.0.0.1:8650（另一扇 tunnel-proxy）

 守护：supervise.ps1 每 8 秒一轮（supervisor.lock 单例锁 + supervisor.heartbeat 心跳）
 自启：计划任务「DSH Phone Access」每 2 分钟 → run-autostart.vbs → autostart.ps1 → start-phone-access.ps1
```

三个关键设计选择，理解了它们就理解了这套系统：

1. **进程间不谈话，用文件当 IPC。** 抓屏进程不认识 HTTP，它只读 `viewers.count`（有没有人看）、`capture.mode`（抓什么）、`capture.interval`（最快多少毫秒一帧），只写命名管道。详见 §2.8。
2. **重活交给两个编译过的 exe**（`capture.exe` / `input.exe`）：PowerShell 截屏会被 AMSI 判成窃取凭据的恶意脚本，而且 workspace 里的文件带低完整性标签会让注入被 UIPI 拦死（`README.md:122-124`、`README.md:574-589`）。
3. **鉴权只有一把 16 进制密钥**（`screen.key`），既是画面服务口令、也是 DSH 长期登录门 `/go` 的口令；没有用户体系、没有 HTTPS。

## 2. 数据流

### 2.1 链路 A：屏幕 → 手机（清晰 / MJPEG，默认模式）

```
capture.exe 主循环（capture.cs Main:712-722）
  ├─ ReadControl() 每 300ms 读 capture.mode        → 变了就重建管线
  ├─ GetSourceRect() 每帧算源矩形（窗口/BitBlt 目标）
  ├─ ReadViewers()==0 → sleep 300ms 空转（不抓屏、0% CPU）
  ├─ 抓屏：窗口被挡 → PrintWindow(PW_RENDERFULLCONTENT)（capture.cs:603-619）
  │        否则 BitBlt 屏幕（:630-631），失败退回 CopyFromScreen（:634-636）
  ├─ 编码线程：双缓冲 → gdst.DrawImage 缩到 outW×outH（:488）→ JPEG q62
  │            → StampJpeg() 插 COM 段 "TSD<unix ms>" 供端到端延迟测量（:164-176）
  └─ pipe.Publish(0, jpeg)：[len:u32][type=0][jpeg]   （:56-61, :85-86）
                           写超时 5s；无客户端时退回写文件（:509-520）
        │
        ▼  命名管道 \\.\pipe\dsh-screen-frames（单实例，capture.cs:70）
screen-server.mjs connectPipe()（:398-446）
  ├─ 4 字节长度帧解析；len==0 = 心跳；8B..64MB 之外视为坏帧清缓冲（:415-419）
  ├─ acceptFrame()：校验 JPEG 头尾 → frame/frameStamp；rtcMode 时同时喂 decoder（:375-387）
  └─ 管道 6 秒没新帧且有人在看 → 主动 destroy 触发重连（:448-451）
        │
        ├─→ GET /stream（MJPEG）:808-887
        │     每 25ms tick（:875）；res.writableLength > max(120KB, 上帧×2.2) 就丢帧（:844-849）
        │     可带 ?w=&q= 让服务端缩小/降质；同一帧同一参数只编码一次（:193-208）
        │     刚连上 1.5 秒内丢帧不计入统计（:847）
        │
        └─→ GET /frame.jpg（省流量轮询）:772-806，也支持 ?w=&q=，命中 thumb 缓存
        │
        ▼
page.mjs：<img src="/stream?...">（双缓冲换流，page.mjs:334-362）
        ├─ /health 每 2s（:982-1059）驱动 HUD、降档（W_LADDER=[2560,1920]，:275-329）、
        │  断流判定（服务端 viewers=0 连续 2 次才重开，:1025-1029）、UIPI 红条（:1002-1021）
        └─ 页面隐藏 → stopped=true（:1061-1069）→ 断流 → viewers.count→0 → 抓屏停
```

**为什么延迟/帧率有三个数**：`in`=管道收到的帧（抓屏产出速度）、`out`=真正推给观看者的唯一帧速度、`drop10`=最近 10 秒丢帧（会自动清零）。定义在 `screen-server.mjs:209-225, 154-186`，页面 HUD 与体检脚本都按这三个口径解释（`README.md:758-786`）。

### 2.2 链路 B：屏幕 → 手机（流畅 / WebRTC）


### 2.5 链路 E：DSH 网页（可选，独立于画面）

## 4. 启动顺序（冷启动）

```
Windows 登录（用户会话；计划任务是用户级，注销后不跑）
 └─1 计划任务「DSH Phone Access」→ wscript → autostart.ps1
       └─1.1 等 WLAN IPv4（最长 4 分钟；拿不到就 exit 1，整条链不启动）   autostart.ps1:13-23
       └─1.2 start-phone-access.ps1
             ├─2 需要一个 LAN IPv4，否则 exit 1（画面服务也不会起）        :54-59
             ├─3 起 DSH：127.0.0.1:8642，等最多 80 秒（40×2s）             :63-80
             ├─4 tailscale status --json 取本机 tailnet IP                 :83-86
             ├─5 起三扇门代理：127.0.0.1:8650 / <LAN>:8642 / <tailip>:8642 :88-91
             ├─6 tailscale serve --bg --http=80 → 127.0.0.1:8650          :94-98
             ├─7 起 supervisor（判锁+心跳；僵死则先杀再起）                :100-130
             ├─8 start-screen.ps1                                         :132-138
             │    ├─8.1 screen.key 不存在则生成 32 位十六进制              start-screen.ps1:41-45
             │    ├─8.2 hosts = [tailnet IP, LAN IP]                      :47-52
             │    ├─8.3 audio.exe（不在跑才起）                            :56-63
             │    ├─8.4 input.exe：先复制到 %LOCALAPPDATA%\DshInput\，
             │    │     若 elevated.enabled + 任务存在 → 启动计划任务；否则普通权限     :67-89
             │    ├─8.5 capture.exe（缺 exe 就先从 .bak 恢复）              :92-108
             │    └─8.6 screen-server.mjs：期望的监听地址少了或多了（DHCP 变了）
             │          就杀掉所有 screen-server 进程重起                   :110-126
             └─9 从 web-lan.log 抓当前 token → 写 URL、重画二维码、拼 /go 永久入口  :140-192
```

**必须遵守的先后依赖**（打乱会坏在哪）：

| 依赖 | 原因 | 违反后的现象 |
|---|---|---|
| 登录会话先于计划任务 | 任务是 Interactive/用户级 | 注销后自启不跑；锁屏仍算登录，OK |
| LAN IPv4 先于一切 | `start-phone-access.ps1:54-59` 硬性 exit | 没 Wi-Fi 的机器/有线机器整条链都不起（见 §8-11） |
| `screen.key` 先于 screen-server / tunnel-proxy | 两者都读同一把 key | 画面页 401；`/go` 503「还没配置访问密钥」 |
| DSH 先于代理与 `/go` | `/go` 要探测 token；代理要转发 | 502「DSH 没有在运行」页 |
| Tailscale 先于 `serve` 与 8660 绑定 | 8660 只 bind tailnet IP + LAN IP | 只绑 LAN；`ts status` 失败则跳过 serve（`:96-98`） |
| capture 与 screen-server 无严格先后 | 服务端每 1s 重连管道 | 顺序反了只是前几秒没画面 |

**幂等性**：所有启动脚本都可重复执行——已在监听就跳过（`start-phone-access.ps1:43-46, 63, 78-80`；`start-screen.ps1:58-63, 93-108, 111-125`）。这正是"每 2 分钟跑一次"能成立的前提。

## 5. 故障模式与自愈

| # | 现象（用户在手机上看到的） | 最可能的根因 | 现有自愈机制（代码位置） | 残留风险 |
|---|---|---|---|---|
| 1 | 页面打不开/一直转圈 | 手机 Tailscale 没连（最常见） | 无代码可治 | 文档级：`手机入口速查.md:85` |
| 2 | 「DSH 没有在运行」 | 8642 进程挂了 | supervisor 连续 2 轮（≈16s）探不到端口就重启（`supervise.ps1:205-219`）；任务 2 分钟内再兜一次 | 更新安装期间被误杀 → 已由维护窗口压制（`:91-108, 155-165`） |

### 6.7 产品化最危险的三个（结论）

1. **`supervise.ps1:9` 的 `$screenIp = '100.108.92.22'`** —— 守护进程的"眼睛"。它用这个地址去问 `/health`（帧新鲜度、注入器是否卡死）。换一台电脑、换一个 tailnet，这个 IP 必然不同，而**失败是静默的**：curl 失败 → 退回看 `screen-latest.jpg` 的 mtime，可管道模式下这个文件根本不更新（`capture.cs:509-520` 只在没有管道客户端时才写文件）。结果：画面卡死、注入器卡死这两类最重要的故障，守护不再处理。
2. **`start-phone-access.ps1:4-7` 的四个绝对路径（dsh.cmd / node.exe / python.exe / tailscale.exe）** —— 它们不是"配置"，是启动脚本的第 4~7 行。DSH 装在别的盘、node 版本不同、Tailscale 非默认装法，任意一条不满足，**整条链在第一步就失败**，而且计划任务会每 2 分钟重复失败一次、只留一行日志。lead 已在 `项目启动.md:48-56` 把"自带 node 运行时"定为第一个工程项，这是对的。
3. **`2560 / 1280` 这一串分辨率常量** —— 它们同时出现在抓屏宽度（`start-screen.ps1:104`）、服务端"满宽透传"判断（`screen-server.mjs:195`）、`/stream` 与 `/frame.jpg` 的上限（`:779,814`）、`publishViewers` 的强制回写（`:256`）、RTC 缩放与轨尺寸（`decode.mjs:6`、`rtc.mjs:21`）。本机是 2560×1600，换了 1920×1080 或 3840×2160 的交付机，这些判断会集体偏掉——表现是"清晰度不对/莫名降档/流畅模式比例怪"，而且**不会报错**。

> 第四危险（并列，值得单独记住）：**端口三元组 8642/8650/8660 + tailscale serve :80**。`survey-report.txt:21` 已经实测出这三个端口在客户机上全部被占用——这不是小概率。

## 8. 待确认 / 已知不一致

> 以下每一条都基于实际文件内容，不是我推测的"可能"。标注了建议动作。

1. **`capture-sources.inc` 不参与编译。** `capture.cs` 没有 `#include`（已 grep 确认），同样的"源选择 + ToI420"代码在 `capture.cs:210-383` 内联存在。两者已开始漂移（例如 `capture.cs:261-265` 的遮挡检测字段在 .inc 里没有）。→ 待确认是否存在另一套构建脚本引用它；建议删除或明确标注"归档"。
2. **抓屏的 `mode=raw` 链路是活的还是死的？** `capture.cs:490-501` 支持直接推 I420，`screen-server.mjs:388-395` 也能收（type=1）；但当前页面的 `postMode()` 永远发 `mode:'mjpeg'`（`page.mjs:255`），服务端 `/rtc-on` 也只置 `rtcMode` 不改 `sourceState.mode`（`screen-server.mjs:566-575`）。→ 实际走的是"JPEG → 服务端解码"（`decode.mjs`）。若没有外部脚本发 `/mode {mode:'raw'}`，这条 I420 直传链路可以删；**待确认**。
3. **`page.mjs:256` 的 1280 宽度是死分支。** 服务端 `publishViewers()` 每 700ms 把宽度强制写回 2560（`screen-server.mjs:244-262`）。→ 不要以为手机切"流畅"会让抓屏降到 1280。
4. **`capture.exe` 的编译目标自相矛盾。** `README.md:127-128` 给的是 `/target:exe`，`README.md:243` 说"用 `/target:winexe` 编译，本身没有控制台"。当前 exe 实际表现（后台无窗口）更像 winexe。→ 重编译前**待确认**用哪个；建议改成 winexe 并修正 README。
5. **密钥位数与 README 不一致。** `README.md:112` 写"32 位十六进制"，但当前 `screen.key` 只有 **16 个字符**（64 bit），与 `README.md:1461`「门的密钥 64 bit」一致。生成逻辑（`start-screen.ps1:42`、`rotate-key.ps1:35-37`）都是 32 位十六进制。→ 当前生产密钥仍是历史遗留的 64 bit，**未轮换过**；`README.md:112` 应改。安全建议：交付前跑一次 `rotate-key.ps1 -Force`。
6. **8780 录屏服务不在本目录。** `手机入口速查.md:70-79` 与 `README.md:1414-1424` 把它列为第三入口（代码在 `D:\dsh-rec\record-server.js`）。本次盘点范围不含它。→ 产品化时是否纳入、是否砍掉，**待确认**（lead 的 `项目启动.md` 决策 7 正是这个问题）。
7. **`start-remote.ps1:25` 的注释是旧的。** 写的是 `127.0.0.1:8650 -> 10.120.222.63:8642`，但实际调用 `Start-Process $node -ArgumentList tunnel-proxy.mjs`（`:28`）不传任何 host/port，走默认值 `127.0.0.1:8650 → 127.0.0.1:8642`。→ 注释误导，建议修掉。
8. **`start-screen.ps1:103` 有一行死代码**（`$capCmd = ...` 定义后未被使用，下一行重新拼了一遍字符串）。
9. **`upgrade-rc3.ps1`/`upgrade-rc3.*` 是一次性升级脚本**，不在启动/守护链路里。→ 待确认是否保留（建议移到 `archive/`）。
10. **WebRTC 原生模块与 Node 版本绑定。** `@roamhq/wrtc` 是原生模块，`node_modules` 随目录走。→ 客户机 Node 版本与 ABI 必须与编译时一致，**待确认**交付时的 Node 版本锁定方式（自带的 node 运行时是最省事的答案）。
11. **`autostart.ps1` 只认 WLAN 接口。** 有线网卡、改名网卡、USB 网卡都可能拿不到 IP → 直接 `exit 1`，整条链不启动（`autostart.ps1:16-23`）。而 `start-phone-access.ps1:13-23` 的 `Get-LanIp` 有兜底（排除 VMware/回环/vEthernet/蓝牙），**但 `start-screen.ps1:28-38` 的兜底还多排除了 Tailscale**。三处逻辑不一致，**待确认**以哪个为准（建议抽成一个函数）。
12. **`screen-server.log` 里会出现成对的 `audio ws connected (1)`**（实测日志尾部）。可能是旧连接未彻底清理后重建，也可能是两个页面同时开。当前不影响功能，**待确认**是否为泄漏（`audioClients` 有 close 处理，理论上会减）。
13. **`supervise.ps1:245,262` 用 `curl.exe` 打 `http://$screenIp:8660/health`**，依赖 Windows 自带 curl 与写死的 tailnet IP。它能免密钥读到 `/health`，是因为源地址与目标地址相同（`ra === la`）命中了 `screen-server.mjs:501-507` 的"本机自连"豁免——**这是能工作的关键细节**：若把服务改成 bind `0.0.0.0`、或从别的机器/地址探测，`/health` 会先被统一鉴权闸门挡住（`:504-507`），守护立刻失去判据。
14. **`viewers.count` 等控制文件的路径是"从 viewersFile 推目录"**（`screen-server.mjs:282-283`）：`capture.interval`/`capture.mode` 都写在 `viewersFile` 所在目录。→ 把 `viewers.count` 挪到别处，抓屏会读不到、永远按默认参数跑（无人看也不停，白烧 CPU）。
15. **README 里的 `capture.exe` 参数说明已过时**（`README.md:109` 只列了 5 个参数，实际 9 个）。→ 以 `capture.cs:686-694` 为准。
